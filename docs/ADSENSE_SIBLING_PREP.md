# 형제 앱 셋 애드센스 준비 계획 (2026-08-11)

> **대상**: inyeonlink · sajulink · dreamslink
> **naming-link은 재심사 동결 중이다**(`docs/POST_LAUNCH_CHECKLIST.md` §A-0). 아래 작업은
> 형제 앱만 건드리며, naming-link의 화면·주소·광고·콘텐츠는 **결과가 나올 때까지 손대지 않는다.**

## 동결선 — 이 문서에서 가장 중요한 규칙

**P0~P2에서 naming-link의 운영 출력이 한 바이트도 바뀌면 안 된다.** 확인한 것과 확인하지
못한 것을 갈라 적는다.

**[확인됨] 형제 앱의 광고 코드는 naming-link과 파일을 공유하지 않는다.** 형제 `layout.tsx`가
쓰는 `@/lib/ads`는 그 앱 자신의 파일이다. `ads.ts`는 앱마다 한 벌씩 따로 있다.

**[확인됨] 빌드가 앱별로 갈린다.** `pnpm --filter <앱> build`이고 도메인도 넷으로 나뉜다.

**[확인 못 함] Vercel 프로젝트 구성은 저장소에서 볼 수 없다.** `vercel.json`은 naminglink에만
있다. 그러니 추정하지 말고 **규칙으로 못 박는다 — 형제 앱만 배포하고 naming-link은 재배포하지
않는다.**

### P1에서 특히 조심할 것

`packages/core`는 **네 앱이 모두 가져다 쓴다.** 그래서 core 작업은 두 갈래로 갈린다.

    core에 새 모듈을 더한다        naminglink는 그것을 부르지 않는다 → 출력 안 바뀜 → 해도 된다
    naminglink의 ads.ts를 core로   naminglink의 소비 코드가 바뀐다  → 출력 바뀜  → 금지

**형제 셋만 core를 쓰게 하고, naming-link은 지금의 240줄 `ads.ts`에 그대로 둔다.**
naming-link의 core 이관은 **심사 결과를 확인한 뒤 맨 마지막**이다. 지금 옮기면 「중복을
없앤다」는 좋은 의도가 동결을 깨는 변경이 된다.

## 0. 먼저 — 이건 「준비」가 아니라 「끄기」다

세 도메인은 **지금 운영에서 모든 화면에 광고를 요청하고 있다.**

    2026-08-11 헤드리스 크롬 실측
    inyeon-link.com / saju-link.com / dreams-link.com
      /en/login · /en/pricing · /en · /en/없는주소   → 넷 다 광고 요청 발생
      pagead2 · googleads.g.doubleclick.net · ep1/ep2.adtrafficquality

    로더가 쓰는 퍼블리셔 ID
      naming-link   (전역 로더 없음 — 고쳐진 상태)
      inyeon·saju·dreams   ca-pub-5084236528895241   ← 셋 다 같은 ID

**「퍼블리셔 ID가 아직 안 켜져 로더가 잠들어 있을 것」이라는 추정은 실측으로 반증됐다.**
켜져 있고, 지금 나간다. 미지원 언어 `/kk`에도 로더가 실린다.

이것이 2026-08-10 naming-link 반려 사유(「발행한 콘텐츠가 없는 화면에 광고」)와 **같은 구조**다.
구글이 이를 계정 단위로 어떻게 볼지는 단정할 수 없으나, 재심사가 도는 중에 같은 모양이 세 곳에
더 있다는 사실은 그대로다.

## 1. 반복을 끊는 것이 이 계획의 핵심이다

세 검토 모두 「naminglink 패치를 세 번 이식」 또는 「세 앱을 한 번에 수정」을 제안했다.
**그 방식이 지금 이 사태를 만들었다.**

    apps/naminglink/src/lib/ads.ts    240줄  ← 8/10~11에 고쳐 갈라짐
    apps/inyeonlink/src/lib/ads.ts    121줄  ┐
    apps/sajulink/src/lib/ads.ts      121줄  ├ 셋은 서로 같다 = 고침 이전 상태
    apps/dreamslink/src/lib/ads.ts    121줄  ┘
    packages/core                     광고 모듈 없음

한 벌을 네 번 복사해 두었으니 **한 곳을 고치면 세 곳이 남는다.** 세 번 이식하면 다음 고침 때
또 네 곳이 된다. 그래서 이 계획은 이식이 아니라 **원본을 하나로 만드는 것**에서 시작한다.

이미 저장소에 적혀 있는 교훈들이다 — 「복제 앱에서 빠지는 건 파일이 아니라 배선」,
「고침은 강제돼야 한다 — 옵셔널은 되돌아간다」, 「앱 목록은 손으로 적지 않는다」.

## P0 — 출혈을 멈춘다 (naming 심사 중에도 할 수 있다)

**목표**: 세 도메인에서 광고 요청 0건. 사이트 연결은 유지.

환경변수를 비우는 방법(`NEXT_PUBLIC_ADSENSE_CLIENT`)이 가장 빠르지만 **되돌아간다** — 다음에
누가 값을 넣으면 전역 로더가 그대로 살아난다. 그래서 P0을 P1의 첫 조각으로 한다.

- [ ] 세 앱 `layout.tsx`에서 **전역 AdSense `<script>` 제거**
- [ ] 같은 자리에 **`google-adsense-account` 소유권 메타 추가**(같은 퍼블리셔 ID) — 로더를
      빼도 사이트 연결이 끊기지 않게 한다(naminglink가 쓰는 방식)
- [ ] `ads.txt` **유지** — 이미 세 앱 다 있다. 건드리지 않는다
- [ ] 형제 셋만 재배포. **naming-link은 재배포하지 않는다**
- [ ] 재배포 후 **운영에서 실측**. 눈으로 세지 않는다

### 완료 기준 — 이보다 느슨하게 잡지 않는다

    홈 · 입력 · 빈 결과 · 가이드 · 약관 · 요금 · 로그인 · 404 후보
      pagead2 · doubleclick · adtrafficquality 요청   각 0건
      AdSense iframe                                  0개
    세 도메인 각각 배포된 운영에서 잰다
    naming-link 운영 출력                             변경 0

`<ins class="adsbygoogle">` 같은 **빈 자리 요소가 남는 것은 P0에서만 임시로 허용한다.** 요청이
안 나가면 P0의 목적은 달성된다. 다만 P1·P3에서 **반드시 없애거나, 허용된 결과 화면에서만
생기게** 한다 — 빈 자리를 남겨 두면 다음 사람이 「광고가 있는 화면」으로 읽는다.

이 시점에서 세 앱의 광고는 **완전히 꺼진다.** 지금도 승인 전이라 수익이 0이므로 잃는 것이 없다.

### 커밋은 둘로 나눈다

    docs  형제 앱 애드센스 준비 계획을 세운다        ← 계획
    fix   형제 앱의 전역 광고 요청을 멈춘다          ← 운영 동작 변경

계획과 동작 변경이 한 커밋에 섞이면 되돌릴 때 계획까지 함께 사라지고, 원인을 추적할 때도
어느 줄이 운영을 바꿨는지 보이지 않는다.

## P1 — `packages/core`에 광고 정책을 한 벌로 옮긴다

**원칙: 정책은 core에, 앱이 정하는 값만 앱에.**

### core로 가는 것 (앱이 못 고치는 것)

    adsConfigured / adsLive / adGatesEnabled 3분할
    ADSENSE_SUPPORTED_LOCALES        구글 지원 언어 (kk·km·mn·uz는 여기 없다)
    HUMAN_REVIEWED_LOCALES           앱별 값이되 타입은 core가 강제
    adsAllowedForLocale(app, locale) 지원 ∩ 사람 검수
    ensureAdsenseLoader()            광고 단위를 그릴 때만 부르는 지연 로더
    adsCspSources                    adsConfigured에 걸린다 (adsLive로 닫으면 안 된다)

### 앱에 남는 것

    퍼블리셔 ID·슬롯 ID (env)
    검수한 로케일 목록 — 지금은 세 앱 다 `{ko}`에서 시작
    **광고가 허용되는 구체적 화면·슬롯·상품 조건**

**경계를 넘지 말 것.** core가 갖는 것은 **판정 규칙과 그것을 어기지 못하게 하는 타입**이고,
**무엇을 파는 어느 화면에 붙일지는 앱이 정한다.** 「중복 제거」가 「모든 앱을 같은 정책으로
강제」로 변하면, 앱마다 다른 상품·화면 구조를 core가 억지로 맞추게 되고 결국 앱이 core를
우회하는 예외를 만든다 — 그게 다시 발산의 시작이다.

### 주의 — 슬롯 이름이 두 갈래다

    naminglink   hanja_result_header · korean_name_result_header · …   결과 화면마다
    형제 셋       top · result · bottom                                 화면 종류별

**형제 쪽 `top`·`bottom`은 결과 화면이 아닌 자리(가이드·약관·입력)에 붙어 있다.** 실제로
`bottom`이 앱마다 6곳, `top`이 2곳 쓰인다. naminglink는 이 배너를 **전부 제거**했고 지금
`placement=` 사용처가 0곳이다.

- [ ] 타입은 `Record<AppKey, …>`로 — `Partial` 금지
- [ ] 로케일 표는 `Record<LocaleCode, …>` — `Record<string>`이면 빠져도 tsc가 조용하다

## P2 — 관문: 빠진 앱이 「통과」가 되지 않게 한다

**이번 사태의 진짜 원인은 검사기가 naminglink만 봤다는 것이다.**
`verify-no-ad-requests.mjs`는 경로·폼·로케일이 naminglink에 박혀 있어 형제 앱을 **아예 세지
않았다.** 결함이 세 곳에 살아 있는데 검사는 초록불이었다.

- [ ] `verify-no-ad-requests.mjs`가 **앱을 인자로 받게** 고친다
- [ ] 앱 목록은 `scripts/app-keys.mjs`의 `APP_KEYS`에서 읽는다 — 손으로 적지 않는다
- [ ] **인자를 안 주면 네 앱을 전부 돈다.** 한 앱이라도 못 돌면 실패다
- [ ] 앱별로 필요한 것(입력 폼 선택자·양성 경로·표본 로케일)은 앱 설정 표로 분리하되,
      **표에 없는 앱은 실패**로 떨어뜨린다. 빠뜨림이 통과로 보이면 안 된다
- [ ] 전역 로더가 되살아나는 것을 잡는 정적 검사도 하나 — `layout.tsx`에 `adsbygoogle.js`가
      있으면 실패. 네 앱 전수, 예외 0개

이 관문이 서기 전에는 P1을 「끝났다」고 부르지 않는다.

## P3 — 앱별로 남는 것

공통 코드가 끝나도 **콘텐츠와 주소는 앱마다 다르다.** 이건 이식으로 해결되지 않는다.

### 세 앱 공통

- [ ] **`not-found.tsx` 신설** — 세 앱 다 없다(naminglink만 있다). 404 상태 + noindex +
      광고 없음 + 홈·주요 서비스 링크
- [ ] **팔지 않는 상품·가격 감추기** — 「가격은 보이는데 구매는 준비 중」 상태를 없앤다.
      naminglink가 쓰는 방식(그리는 쪽에서 감춘다)을 따른다
- [ ] **광고 허용 로케일 = `{ko}`로 시작** — 지원 23개와 색인 대상과 광고 대상은 서로 다른
      목록이다. 검수한 로케일이 늘면 `docs/LOCALE_REVIEW_LOG.md`에 적고 늘린다

### 앱별 주소 규모

    inyeon   sitemap  480   무접두 20
    saju     sitemap  504   무접두 21
    dreams   sitemap 1176   무접두 238
    (naming은 정리를 거쳐 365)

- [ ] **inyeon** — 서치 콘솔 자료가 이미 있다. 미색인 248개가 현재 sitemap과 겹치고, 구글이
      다른 canonical을 고른 군집 17개가 열려 있다(`docs/issues/SEARCH_CONSOLE_COVERAGE_2026-08-08.md`).
      **23로케일을 일괄 noindex로 바꾸지 말 것** — 이미 쌓인 색인을 버리게 된다
- [ ] **saju** — 색인 이력이 적다. 처음부터 검수한 로케일만 sitemap·색인 대상으로 좁히는 편이
      유리하다
- [ ] **dreams** — 1,176개가 가장 크다. 꿈 상징 사전은 세 앱 중 **독자 콘텐츠 근거가 가장
      강하지만**, 얇은 목록·빈 검색 화면이 함께 색인되면 그것이 반려 사유가 된다. 대량 URL의
      두께를 먼저 재고 나서 정한다

## P4 — 순서와 조건

```
P0 출혈 멈추기        ← 지금. naming 동결과 무관
  └ P1 core 한 벌
       └ P2 관문(앱 인자 + 전수)
            └ P3 앱별 콘텐츠·주소·404·상품
                 └ naming-link 심사 결과 ⏳
                      └ inyeon → saju → dreams  하나씩
```

**동시에 넣지 않는다.** 하나의 결과에서 배운 것을 다음에 반영한다. 콘솔에 사이트를 추가하는
것도 naming-link 결과 뒤다 — 심사 중에 색인 0인 도메인을 더하면 심사자가 볼 표면만 늘어난다.
**뺐다 다시 넣는 것은 말리는 방식**이라 한 번에 제대로 넣어야 한다.

순서를 inyeon부터로 둔 것은 콘텐츠·법적 문서·23로케일 완성도가 가장 높고 서치 콘솔 기준선이
이미 있기 때문이다. **다만 dreams는 「무료가 본체·광고가 주 수익」인 서비스라 수익 관점의
우선순위는 가장 높다.** naming-link 결과를 본 뒤 이 순서를 다시 정할 여지를 남긴다.

## 이 계획이 막으려는 반복

| 지난 실패 | 여기서 막는 자리 |
| --- | --- |
| 고침이 한 앱에만 들어가고 형제는 옛 상태로 남음 | P1 — 원본을 core 한 벌로 |
| 검사기가 한 앱만 보고 「ALL PASS」 | P2 — 앱 목록을 `APP_KEYS`에서, 빠지면 실패 |
| 파일은 다 있는데 아무도 안 부름 | P2 — 정적 검사 + 실제 요청 실측 두 축 |
| 옵셔널 고침이 되돌아감 | P0을 env가 아니라 코드로 |
| 관문 없이 비싼 단계부터 시작 | P2가 서기 전에 P1을 끝났다고 부르지 않음 |
