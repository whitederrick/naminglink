## 갈래 A — 애드센스

```
naming-link 심사 결과  ⏳
  └─ A-1  인연링크를 애드센스에 사이트 추가
       └─ A-2  인연링크 광고 슬롯 ID 등록          ← 여기부터 광고가 실제로 나온다
            └─ A-3  지표 초기화
```

### A-1 인연링크를 애드센스에 사이트 추가

**조건**: naming-link 심사 결과가 나온 뒤.

- [ ] 애드센스에 `inyeon-link.com` 추가
- [ ] `NEXT_PUBLIC_ADSENSE_CLIENT` 등록 후 **재배포** — 안 하면 로더가 붙지 않는다
      (슬롯은 비워 두면 운영 빌드에서 아무것도 그리지 않는다)

**왜 지금 안 하는가**: 계정 첫 승인이 걸린 상태다. 지금 얹어도 광고가 안 나와 **얻는 것이 없고**,
갓 연결해 색인 0인 도메인을 심사 중에 더하면 **심사자가 볼 표면만 늘어난다.** 승인 후에 하면
그때는 색인도 쌓여 있다.

### A-2 인연링크 광고 슬롯 ID 등록

- [ ] 슬롯 ID 입력 — **이 시점부터 인연링크에 광고가 실제로 나온다**
- [ ] `NEXT_PUBLIC_GAM_REWARDED_UNIT`에 보상형 광고 단위(`/네트워크코드/이름`) → 재배포

자리별 구조는 정해져 있다: 진입=오퍼월, 후보 열기=GAM 보상형, 폴백은 전부 셀프 광고.
`header` 슬롯은 폐지됐다(2026-07-31).

**제출 버튼 문구는 따로 고치지 않는다**(2026-08-04). 광고 단위를 넣으면 관문과 함께 문구도
켜진다 — 지금은 `궁합 보기`, 그때는 `광고 확인 후 궁합 보기`다. 23로케일 두 벌이 이미 들어
있다(`submit` / `submitNoAd`).

### A-3 지표 초기화

**조건**: 광고가 **실제로 붙은** 시점. 그 전에 지우면 붙기 전 숫자를 지우는 것이 된다.

- [ ] AI 사용량 · 글로벌 접속/활용 · 광고 3종을 0으로
- [ ] **주문·상품 설정은 건드리지 않는다**

## 갈래 B — 국내 결제

```
토스 키  ⏳   +   통신판매업 신고번호  ⏳
  └─ B-1  상품 판매 켜기
       └─ B-2  실주문으로 결제→생성 배선 확인
            └─ B-3  테스트 채널 흔적 지우기
                 └─ B-4  엄격 CSP(nonce)
```

### B-0 통신판매업 신고번호

- [ ] 등록 — 넣으면 푸터·약관·문의 페이지에 **자동 반영**된다(따로 고칠 곳 없음)

### B-1 상품 판매 켜기

**조건**: 토스 키.

지금 상품 20건이 전부 `product_settings.enabled=false`다. 살 수 있으려면 **상품 enabled AND
결제 키** 둘 다여야 한다 — 키 없이 켜 두면 죽은 구매 버튼이 생긴다(2026-07-29에 그래서 내렸다).

- [ ] 관리자 화면에서 켜기(또는 `scripts/toggle-products.mjs` — 이력도 함께 남는다)
- [ ] 인연링크 가격·주문도 같은 상태다. 함께 켠다

### B-2 실주문으로 결제→생성 배선 확인

번역·렌더는 직접 불러 확인했지만(2026-08-01), **주문 → 결제 → 생성 라우트로 이어지는 배선은
실주문으로 태워 보지 못했다.**

- [ ] **아랍어(ar) 로케일로 한 건** — 한글 아트 PDF. 해설이 영어로 번역돼 나오는 경로다
      (`hangul-art-translate.ts`가 **결제 후에만** 돈다 — 무료 경로로는 확인이 안 된다)
- [ ] 국내 결제 한 건(토스)
- [ ] 굿즈(도장) 실결제 — 배송 정보 입력까지
- [ ] 재발급 한도(`REISSUE_LIMIT`) 동작 확인
- [ ] **같은 결제로 다른 결과를 열어 보기** — 2026-08-04에 고친 자리다. 한 주문이 결과 한 벌에만
      묶이는지 실결제로 확인한다. 두 앱 모두 해당한다.

      1. 결제한 뒤 그 결과를 연다(정상)
      2. **같은 주문 정보로 다른 입력의 결과를 열어 본다** → 거절돼야 한다
         (naminglink는 "이 결제로는 다른 결과를 열 수 없습니다", 인연링크는 `INPUT_MISMATCH`)
      3. 처음 열었던 결과를 **다른 창에서 다시** 연다 → 열려야 한다(정상 경우가 막히면 안 된다)

      **왜 굳이 실결제로 하는가**: 지금은 `scripts/verify-order-binding.mjs`가 DB에 대고 동시
      다섯을 던져 하나만 성공하는 것까지 확인했지만, **결제 확인을 거쳐 들어오는 경로 전체는
      태워 보지 못했다.** 결속을 조건부 쓰기로 바꾸면서 실패 갈래가 늘었으므로, 정상 이용자가
      막히는 쪽(3번)을 특히 볼 것.

### B-3 테스트 채널 흔적 지우기

**조건**: 실채널 전환 시점.

- [ ] `PORTONE_ALLOW_TEST_CHANNEL` 값 삭제 — **사고 위험은 2026-08-02에 이미 막았다.**
      두 앱 모두 `isDevEnvironment()` 가드가 있어 운영 배포에서는 이 값이 켜져 있어도 무시된다
      (`lib/portone.ts`의 `isTestChannelAllowed`, 검사는 `scripts/verify-test-channel-guard.ts`).
      값을 지우는 것은 "안 쓰는 스위치를 남기지 않는다"는 정리 차원이다.
      실채널 배선을 미리 보려면 **Preview 배포에 `APP_ENV=dev`**를 넣고 거기서 한다
- [ ] 웹훅 시크릿 교체
- [ ] 테스트 주문·세션 일괄 삭제(오픈 시 방침)

### B-4 엄격 CSP(nonce)

**조건**: 실결제를 한 바퀴 돌린 뒤 · 스테이징에서 검증 후.

지금도 CSP는 **전 경로에 적용돼 있다**(`next.config.ts`의 `securityHeaders`). 남은 것은
`script-src`의 `'unsafe-inline'`을 없애고 nonce로 바꾸는 것뿐이다.

**왜 B-2 뒤인가**: 결제·광고 SDK(토스·포트원·애드센스·GAM)가 인라인 실행에 의존하는 부분이
있어, 켜는 순간 **결제가 막히는 사고**가 날 수 있다. 실거래를 검증하기 전에는 **그 사고를
감지할 방법도 없다.** 반면 이 서비스는 남의 글을 보여 주지 않아 XSS 유입 경로가 좁다 —
위험 대비 실익이 낮다.

- [ ] 스테이징에서 nonce CSP 적용
- [ ] 결제 한 바퀴(토스·페이팔) · 광고 한 바퀴(애드센스·GAM 보상형·오퍼월) 확인
- [ ] 콘솔에 CSP 위반이 없는지 확인한 뒤 운영 적용

## 상시로 도는 것

사슬에 매이지 않는다. 제 리듬으로 돈다.

### 코드를 건드린 날 돌리는 것

**손으로 맞추면 반드시 하나가 빠진다**(2026-08-04에 여덟 건 중 넷이 그 원인이었다). 그래서
사람이 아니라 아래가 센다. 라우트를 더하거나 푸터·메뉴를 손댔으면 그날 돌린다.

```
node scripts/verify-route-guards.mjs                                  # 서버 없이
node scripts/verify-reachable-links.mjs naminglink http://localhost:3099   # dev 서버 필요
node scripts/verify-reachable-links.mjs inyeonlink http://localhost:3097
```

- **`verify-route-guards`** — 무인증으로 부를 수 있는 라우트가 본문 크기와 호출 횟수를 재는지
  전수로 센다. 예외는 파일 안에 이유와 함께 적는다(지금은 0개다).
- **`verify-reachable-links`** — 소개·문의하기·공지사항·이용 안내에 **화면에서 실제로 닿는지**
  본다. 파일이 있는지가 아니다 — 셋 다 있는데 아무 데서도 안 보이던 적이 있다.

둘 다 대조군이 들어 있어 검사기 자체가 고장 나면 실패로 떨어진다.

### 기준 자료 점검(분기 1회)

**다음 확인 시점 — 2026년 4분기.**

바뀌는 것은 **인명용 한자표 하나**다. 2~3년 간격으로 개정되고 마지막이 2024-06-11이라 이미
확인 구간이다. 2026-08-02에 음절 488개를 전부 대조해 **개정 없음**을 확인했다.

```
node scripts/check-official-hanja-revision.mjs 500   # 몇 분. 개정 여부만 본다
npm run official:sync                               # 달라졌을 때만
```

동기화 스크립트는 받은 글자 수가 마지막 개정의 발표 수와 어긋나면 **멈춘다**(예전에는 조용한
플래그였고 아무도 보지 않았다). 개정이 오면 `REVISIONS`에 한 줄 더하고 다시 돌린다.

- [ ] 분기 점검 · 달라지면 동기화 후 **공지사항에 한 항목**

### 공지사항 리듬

애드센스 항목 중 **유일하게 "앞으로"로 남은 칸**이다. 한 번의 작업이 아니라 습관이라 체크박스로
끝나지 않는다.

`/notice`는 개발 일지가 아니다. 판 적 없는 것의 "변경", 약관에 없는 고지 기간, 결함 경위는
적지 않는다. 반대로 **엔진 규칙으로 점수가 움직이면 반드시 올린다** — 이미 결과를 가진 사람의
숫자가 달라지기 때문이다. 기준은 `lib/notices.ts` 첫머리에 있다.

- [ ] 며칠 뒤 `색인 생성 → 페이지`의 "생성되지 않음" 사유 확인

## 조건이 서기 전엔 하지 않는 것

**"아직 안 함"이 아니라 "지금은 하지 않기로 한 것"이다.** 조건을 적어 두지 않으면 다음에 보는
사람이 그냥 해 버린다.

### `sharp` 취약점

**조건**: 아래 셋 중 **하나라도** 해당되는 순간. 그전에는 올리지 않는다(2026-08-03 결정).

`sharp@0.34.5`에 high 등급 CVE 4건이 있다(libvips 상속, GIF·TIFF·VIPS). 패치는 `0.35.0`부터인데
**Next 16.2.11이 `sharp: "^0.34.5"`를 선언**하고 있어(0.x 캐럿은 `<0.35.0`) 올리려면
`pnpm.overrides`로 Next의 선언을 강제로 무시해야 한다. 근거와 노출면 분석은
`docs/AUDIT_2026-08-03.md` §3-1에 있다.

**지금 안 하는 이유 한 줄**: 이 취약점은 **신뢰할 수 없는 이미지를 처리해야** 성립하는데, 지금은
그런 이미지가 들어올 자리가 없다(자체 자산 · 관리자 업로드 · 서버 생성 셋뿐이고 `remotePatterns`도
없다).

- [ ] **Next을 올릴 때 함께** — Next이 `^0.35`로 올리면 override 없이 따라온다. **가장 깔끔한 길**
- [ ] **이용자 이미지 업로드를 열면** — 그 순간 신뢰할 수 없는 입력이 생긴다. **필수**
- [ ] **`images.remotePatterns`를 추가하면** — 외부 URL이 최적화 경로로 들어온다. **필수**

override로 먼저 올리는 경우에는 두 앱의 이미지가 **실제로 최적화되는지** 확인할 것
(`/_next/image` 응답의 `Content-Type`이 webp/avif로 바뀌는지). 조용히 깨지면 랜딩 첫 화면이
무거워진다 — `BrandMark.tsx` 주석에 1024×1024 원본 964KB가 그대로 내려간 전례가 있다.

### 아랍어·크메르어 PDF 문단

**조건**: 라이브러리가 고쳐지면.

지금은 문서를 영어로 내되 **서체는 등록**해 뒀다(죽는 것은 문단이지 이름이 아니다).

- [ ] 고쳐지면 `PDF_FALLBACK_TO_EN`을 비운다 — `render-report-scripts.tsx`가 그 자리를 계속
      시험하고 있어 **성공하면 알려 준다**

### 광고 잠금 서버화에서 배운 것

②는 원래 "GAM 보상형의 SSV 콜백을 받아 일회용 토큰을 발급한다"는 계획이었다. **그 계획은
성립하지 않는다.** 웹 보상형에는 SSV가 없다:

> Server-side verification is an app only feature and it is unavailable for web use.
> — [Ad Manager Help](https://support.google.com/admanager/answer/9116812)

슬롯을 붙여도 오지 않을 콜백이었다. **증명할 수 없다면 부과할 수 있는 것은 시간뿐이다.**
광고를 시작할 때 서버가 표를 끊어 준비 시각을 적고, 후보를 열 때 그 표를 받아 쓴다.
보관하는 것은 표의 해시·방문자 해시·시각뿐이라 **미저장 원칙과 충돌하지 않는다.**

```
lib/unlock-ticket.ts                      발급·사용(server-only)
api/candidates/unlock-ticket              광고를 시작할 때 부른다
supabase/…_unlock_tickets.sql             줄 세우기·만료·정리가 전부 여기 있다
scripts/verify-unlock-ticket.mjs          실제 DB에 대고 확인(13항목)
```

**남는 한계**: 방문자 판정이 IP 기반이라 IP를 갈아 가며 병렬로 도는 것은 여전히 가능하다.
다만 그때도 후보 하나에 정직한 이용자와 같은 시간이 들고 시간당 60건 제한이 걸린다.
광고를 안 보고 **즉시·무제한**이던 것은 끝났다.
