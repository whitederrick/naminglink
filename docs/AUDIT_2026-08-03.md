## 2. 고친 것

### 2-1. `admin_pii_access_logs` — 감사받는 쪽이 지울 수 있는 로그였다

```
admin_pii_access_logs   anon           DELETE,INSERT,TRUNCATE,SELECT,UPDATE,…
admin_pii_access_logs   authenticated  DELETE,INSERT,TRUNCATE,SELECT,UPDATE,…
```

이 표는 관리자가 배송지(개인정보)를 언제 열어 봤는지 남기는 **감사 기록**이다. 만든
마이그레이션(`20260727150000`)이 RLS만 켜고 `revoke`를 빠뜨렸다.

**지금 뚫려 있던 것은 아니다** — RLS가 켜져 있고 정책이 0개라 전부 거부된다. 문제는 정책이
하나라도 생기는 순간 열린다는 것이고, 하필 감사 로그다. 그리고 그 파일의 주석은 이미
"서비스 롤로만 읽고 쓴다"고 적어 두었는데 권한이 그것을 따르지 않았다.

`rate_limit_counters`·`unlock_tickets` 등 이 저장소의 다른 표는 전부 revoke가 붙어 있다.
그 규칙에 맞췄다.

### 2-2. `increment_font_picks` — 인증 없이 부를 수 있는 쓰기 함수였다

```sql
SECURITY DEFINER · anon=true · authenticated=true
update report_fonts set pick_count = pick_count + 1 where code = any(font_codes)
```

**anon 키는 클라이언트 번들에 들어 있는 공개값이다.** 누구나 이 RPC를 직접 불러 서체
인기순위를 무제한 올릴 수 있었고, DB 쓰기 부하도 만들 수 있었다.

부르는 곳은 `api/premium-reports/global-order`(service_role) **한 곳뿐**이라 이 권한 자체가
필요 없었다. Postgres가 함수에 PUBLIC EXECUTE를 기본으로 주는 것을 revoke하지 않은 것이다.
같은 저장소의 다른 SECURITY DEFINER 함수 6개는 전부 service_role 전용이었다 — 이것만
예외였다.

두 항목 모두 `supabase/migrations/20260803120000_tighten_grants.sql`로 적용·검증했다.

### 2-3. 한자 DB 검사기가 **절대 통과할 수 없는 상태**였다

```
Count mismatch before publish: {"hanjaEntries":9938, …}   ← 기대값 10380
```

`10380`은 최초 커밋(`8b3e9bf`)에 박힌 뒤 한 번도 갱신되지 않았다. **데이터는 정상이고
검사기가 낡은 것이었다.**

| 숫자 | 뜻 |
| --- | --- |
| 10,380 | **원본 추출 행 수** — 검사기가 멈춰 있던 값 |
| 9,938 | 현재 DB 행 수. 2026-07-20에 화면에 그릴 수 없는 코드(미할당 Plane 10 · PUA) **442행을 걷어낸** 결과 |
| 9,088 | 그중 후보로 낼 수 있는 고유 글자 |
| 488 | 음절 |

근거: `docs/WORK_STATUS_2026-07-20.md:58`(442건 삭제, 백업 `bad-hanja-backup.json`),
`docs/REFERENCE_DATA_UPDATES.md:13`("원본 추출 10,380행 · DB 9,938행").

**고치면서 두 가지가 더 드러났다.**

첫째, `10380`이 **세 군데**(59·179·182줄)에 있었다. 상수 하나로 모았다.

둘째, 그 뒤에 있던 **공개 조회 검사가 앱이 쓰지 않는 경로를 보고 있었다.** anon 키로
`official_hanja_entries`를 읽는지 확인했는데, 화면에 쓰이는 조회는 전부 서버에서
service_role로 돈다(`lib/hanja-guide-data.ts`, `lib/official-hanja-db.ts`,
`api/hanja/surname`). 안 쓰는 경로를 검사하면 **진짜 화면이 깨져도 통과하고**, 반대로 권한을
조이면 멀쩡한데도 실패한다 — 실제로 `permission denied`로 멈춰 있었다.

그래서 둘로 갈랐다.
- **데이터 검사**는 service_role로 옮겼다(남 31자 · 규 38자 실제 조회 확인).
- **권한 검사**는 뒤집었다 — anon 키로는 **읽히지 않아야 한다**. 이 표는 손질을 거친 자료이고
  화면에는 서버가 골라서 내보낸다. 나중에 누가 편의로 열어 두는 것을 여기서 잡는다.

개정이 오면 이 값을 함께 갱신해야 한다는 절차도 주석에 적었다(REVISIONS · EXPECTED · 문서 셋).

**최종 결과**
```json
{ "ok": true,
  "after": { "hanjaEntries": 9938, "hanjaProductionEntries": 9938,
             "pronunciationEntries": 2321, "namCandidates": 31,
             "gyuCandidates": 38, "anonReadBlocked": true } }
```

## 3. 남겨 둔 것

### 3-1. `sharp <0.35.0` — high 등급 CVE 4건

CVE-2026-33327 / 33328 / 35590 / 35591(libvips 상속). `next`의 **전이 의존성**이라 두 앱 모두
해당한다. 오버라이드로 올릴 수 있지만 Next 이미지 최적화 경로에 영향을 줄 수 있어 별도로
확인이 필요하다. 이 서비스는 이용자가 올린 이미지를 처리하지 않으므로(관리자 업로드만) 노출
면은 좁다.

### 3-2. inyeonlink 본문 크기 제한 부재

`readJsonBodyLimited`가 **1개 라우트**에만 있다(naminglink는 12개). zod가 파싱 후 필드를
막지만 **원문은 일단 메모리로 읽는다.** 두 앱이 일부러 같은 규칙을 쓰기로 한 자리라
(`lib/portone.ts` 첫머리: "검증 규칙이 갈리면 한쪽에만 구멍이 생긴다") 맞춰 두는 편이 낫다.

### 3-3. inyeonlink 결제 설정 모듈이 클라이언트 그래프에 들어 있다

```js
o.default.env.NEXT_PUBLIC_TOSS_CLIENT_KEY && o.default.env.TOSS_SECRET_KEY, …
```

**값은 새지 않는다** — Next는 `NEXT_PUBLIC_`만 인라인하고, 이 표현식의 결과는 버려진다.
다만 `payments-csp.ts`·`toss.ts`가 클라이언트 번들 그래프에 들어 있다는 뜻이고, 나중에 누가
거기서 무언가를 client component로 가져다 쓰면 **브라우저에서는 조용히 false**가 된다.
naminglink는 같은 검사에서 깨끗했다.

### 3-4. 그 밖

- `X-Powered-By: Next.js`(양쪽) — `poweredByHeader: false` 한 줄
- `official_*` 표의 공개 읽기 RLS 정책이 **닿지 않는 채로 남아 있다**(GRANT가 없어 무효).
  지금은 무해하지만 "정책이 있으니 공개인가 보다"라는 오해를 부른다
- 테스트 데이터: orders 4건(전부 `is_test=true`·UNPAID), premium_analysis_sessions 3건
  (DELETED) — 오픈 시 정리 목록에 이미 있다

## 4. 확인된 정상 — 어떻게 확인했는가

### 4-1. 서버 비밀이 브라우저로 나가지 않는다

**이름이 아니라 실제 값으로 검사했다.** 이름만 찾으면 값이 다른 경로로 흘러갔을 때 못 잡는다.
`.env.local`의 서버 전용 값 10종(service_role 키 · OpenAI · DB URL · `RESULT_SEAL_SECRET` ·
웹훅 시크릿 · `CRON_SECRET` · `ANALYTICS_HASH_SALT` 등)을 브라우저 자산 49개에서 전수 탐색 —
**하나도 없다**. 검사기는 `scripts/audit-bundle-secrets.mjs`로 남겼다.

### 4-2. 결제 승인 경로

`api/payments/toss/confirm`:
- 금액을 **주문에 저장된 값**으로 승인한다(돌아온 쿼리의 amount를 쓰지 않는다)
- 열린 리디렉트 차단(`/`로 시작하고 `//`가 아닌 경로만)
- `orderId`는 UUID 형식 검증
- 이미 PAID면 멱등하게 통과(새로고침·뒤로가기 대비)
- 승인 실패 시 결제도 성립하지 않는다(토스는 승인해야 결제가 된다)

### 4-3. 관리자 인증

`lib/admin-auth.ts` — Bearer 토큰 → `supabase.auth.getUser()` **서버 검증** →
**`app_metadata`** 의 역할 확인. 이용자가 고칠 수 있는 `user_metadata`가 아니다. 단수 `role`과
배열 `roles`를 모두 본다(한쪽만 보면 배열로 부여된 관리자가 회원 목록에 섞인다).
토큰 없음 401 · 세션 무효 401 · 권한 없음 403 · 설정 없음 503으로 전부 fail-closed.

### 4-4. DB 자세

- **테이블 30개 전부 RLS 활성**
- SECURITY DEFINER 함수 7개 전부 `search_path` 고정
- 조치 후 anon/authenticated 권한이 남은 표는 `naming_logs` 하나뿐이고, 그것은 의도된
  것이다(본인 기록 읽기·삭제, 정책 2개가 `auth.uid() = user_id`로 제한)
- `is_test` 안전망: `orders`·`premium_analysis_sessions` 양쪽 `NOT NULL` · 기본값 없음
  (빠뜨린 INSERT가 에러로 실패한다)

### 4-6. 검사 스크립트

**32개 중 30개 통과.** 나머지 둘은 실행 조건 문제였다.

- `verify-official-database.mjs` — §2-3에서 고침, 이제 통과
- `validate-official-reference-data.mjs` — 원본 `docs/hanja.pdf`가 저장소에 없어 못 돈다

**함정 하나**: 서버 전용 모듈을 부르는 검사는 `--tsconfig scripts/tsconfig.sweep.json`으로

## 6. 이번 감사에서 배운 것

**안 도는 검사는 지키지 않는 검사다.** 이번에 실패한 6개 중 4개는 실행법 문제였고 2개는
진짜였는데, 겉보기로는 구별되지 않았다. 검사기가 조용히 죽어 있으면 "통과"와 "안 봄"이
같아 보인다.

**기대값을 현실에 맞추기 전에 현실이 맞는지 봐야 한다.** 한자 검사기의 10,380을 9,938로
바꾸는 것은 5초면 되지만, 그 감소가 의도된 정리인지 유실인지 모르면 검사를 무력화하는
것이 된다. 문서에서 근거(442행 삭제·백업 위치)를 찾은 뒤에 고쳤다.

**"이 자리만 예외"가 위험 신호다.** 이번에 나온 셋은 전부 저장소의 다른 자리에서는 지켜지는
규칙이었다 — revoke 붙은 표 29개 중 하나만 빠짐, service_role 전용 함수 6개 중 하나만 열림,
갱신된 상수들 중 하나만 멈춤.
