## 1. 무엇을 더할 것인가 — 지어내지 않는다

사용자 요구는 "PDF가 더 풍성해야 구매로 이어진다"였다. 처음 제안은 **화면을 요약으로 줄이고
PDF를 키우는** 것이었는데, 세 가지와 충돌해 되돌렸다(사용자 동의).

- 애드센스가 보는 콘텐츠 분량이 줄어든다 — 어제 안내 문서를 만든 목적과 반대다
- 광고 수익이 화면 체류에서 나온다. 결과 화면이 짧아지면 중간 광고 자리가 죽는다
- 원래 보여 주던 것을 거두면 이용자는 "줄었다"고 느낀다

그래서 **화면은 그대로 두고 리포트에만 더한다**로 정했다. 문제는 무엇을 더하느냐다. 지어내면
명리 해석을 새로 쓰는 셈이고, 그건 이 서비스가 하지 않기로 한 일이다.

엔진을 훑어 두 갈래를 찾았다.

**① 계산 과정에서 나왔다가 버려지던 값**

| 값 | 어디 있었나 |
| --- | --- |
| 방향별 보완 점수 | `saju.ts`가 평균만 내보내고 양쪽 값은 버렸다 |
| 일간 짝의 이름(여섯 종) | 점수로만 쓰고 종류는 버렸다 |
| 진태양시 보정 내역 | `prepare`가 받아 놓고 버렸다 |
| 왕상휴수사·월령 전후 세력·환절기 | 완전 미사용 |
| 양력↔음력 변환 | 완전 미사용 |

**② 규칙은 있는데 적용하지 않던 자리**

지지 관계는 일지 하나만 봤다. 네 기둥 전부에 같은 함수를 부르면 표가 나온다. 십신도 일간
끼리만 봤다. 상대의 어느 자리가 내게 무엇인지는 알 수 없었다.

**②를 점수에 넣지 않는다.** 넣으면 총점이 달라져 이미 나간 결과 링크와 어긋난다.

## 2. 엔진 (`970caea`)

심화 자료를 `engines/detail.ts`로 갈랐다. 점수 계산과 한 파일에 섞으면 규칙이 두 곳에서
만들어지고, 같은 입력에 다른 답이 나오면 유료 상품에서는 환불 사유가 된다.

`matchDetail`은 `saju.ts`가 쓰는 것과 **같은 함수**를 부른다(`resolveYongsin`·`supplyScore`·
`branchRelation`·`tenGod`). 따로 계산하면 리포트의 숫자와 점수의 근거가 갈린다.

`ENGINE_VERSION`을 v10으로 올렸다. 점수 규칙이 그대로라도 결과의 모양이 달라졌으면 번호를
올리는 것이 이 저장소의 관례다(v4가 같은 이유로 올렸다).

**검증이 핵심이었다.** 회귀 하니스가 `변동 없음 — 베이스라인과 일치`를 냈고, 베이스라인 diff는
**버전 문자열 한 줄뿐**이다. 모든 점수가 글자 단위로 같다.

## 4. 기존 결함 셋

가격을 올리려다 세 가지가 드러났다. 전부 원래 있던 것이고, 이번 변경이 만든 것이 아니다.

### ① 비라틴 문자가 깨져 있었다 (`f40f04d` · `b905a15` · `58ecd9b`)

PDF가 **한글·CJK·라틴 세 서체만** 등록하고 있었다. 화면 문구가 ko·en뿐이던 시절의 설정인데
사전이 23로케일로 늘어난 뒤에도 남아 있었다. 서체 파일은 이미 앱에 있었고 **등록만 빠져
있었다.** 태국어·힌디어가 살아났다.

**아랍어·크메르어는 등록하면 렌더가 죽는다.** 처음에는 "라이브러리 한계"로 적었는데 근거가
얕았다 — naminglink는 그 둘을 등록해 두었으니 되는 것 아니냐는 지적을 받고 다시 팠다.

원인까지 좁혔다. `@react-pdf/textkit`의 `reorderLine`이 **글자 위치로 글리프 배열을 색인**한다.

```js
const glyph = getItemAtIndex(line.runs, 'glyphs', index);
if (addedGlyphs.has(glyph.id))   // glyph가 undefined면 여기서 죽는다
```

아랍어는 셰이핑에서 두 글자가 한 글리프로 합쳐지므로(لا 등) **글리프 수 < 글자 수**가 되고
색인이 배열을 넘는다. 크메르어의 결합 문자도 같다. 사전 문자열 850개를 하나씩 렌더해
좁힌 결과 원인이 **둘**이었다.

1. `**강조**` 표기 — `*`가 중립 문자라 RTL 구간 한가운데에 경계를 만든다. 아랍어 12개가
   여기서 죽었고, 별표를 걷어내니 850개가 전부 통과했다.
2. **줄바꿈이 일어나는 아랍어 문단** — 이건 무엇을 해도 안 된다. 짧은 문자열은 앞에
   RLM(U+200F)을 붙이면 살아나지만 문단이 두 줄이 되는 순간 실패한다. 한자를 빼도,
   라틴 구간을 격리 문자로 감싸도 마찬가지다. `@react-pdf/renderer`는 이미 최신(4.5.1)이라
   올릴 버전도 없다.

**naminglink도 똑같이 죽는다**(실측). 실제 판매 PDF(`renderHangulArtPdf`)에 긴 아랍어 문단을
넣어 확인했다. 그쪽은 아랍어로 뽑아 본 적이 없어 드러나지 않았을 뿐이다.

**그래서 아랍어·크메르어 리포트는 영어로 낸다**(사용자 결정). `pdfLocale()` 한 곳이 판단하고
`report/pdf` 라우트가 부른다. 화면은 그대로 아랍어·크메르어다. 구매 패널에 **결제 전 고지**를
띄운다(`pdfLanguageNotice`, 23로케일). 라이브러리가 고쳐지면 목록을 비우는 것으로 되돌린다.

부수적으로 `MixedText`가 `**`를 걷어내게 했다. `plain()`으로 처리하고 있었지만 호출하는
자리에서만 걸렸고 143곳이 그냥 지나가고 있었다.

`scripts/render-report-scripts.tsx`를 남겼다. 문자 체계가 다른 로케일 열 개로 PDF를 만들고
**PNG로 보라고** 안내한다 — 서체 누락은 오류 없이 통과하고 글리프만 빠진다.

### ② 약관이 궁합 가격만 고지하고 있었다 (`85c9ec5`)

`terms`·`pricing`·`refund`·`privacy` 네 화면이 모두 `getReportPrices()`를 **기본 인자로** 불렀다.
두 상품이 같은 값이던 동안에는 우연히 맞았지만, 궁합만 올리는 순간 인연의 결 가격이 문서에서
틀린 값이 된다.

더 나쁜 것도 있었다 — **인연의 결 리포트가 약관·요금안내에 아예 없었다.** 파는 상품이 둘인데
고지된 것은 하나였다.

문서가 가격을 하나만 받던 구조를 `AllReportPrices`로 넓히고 요금안내에 인연의 결 절을 넣었다.
플레이스홀더 둘을 더하되 기존 `{priceDomestic}`의 뜻은 **궁합 가격 그대로** 뒀다 — 이름을 갈면
번역된 21개 파일을 전부 손대야 한다.

### ③ naminglink 안내 문서가 색인 목록에 없었다 (`1f8e866`)

안내 문서 열한 편을 애드센스용 콘텐츠로 만들어 놓고 **sitemap에 한 편도 넣지 않았다.**
216 URL은 서비스·약관 아홉 경로 × 24였다. 인연링크는 처음부터 `guide-index`에서 경로를 받아
오는 구조라 이 문제가 없었다.

경로를 손으로 적지 않고 `guideEntries`에서 받아 오게 고쳤다. **216 → 552 URL.**

## 6. "무엇을 파는가" 안내 문서 (`1f8e866`)

파는 물건이 무엇인지 사기 전에 읽을 곳이 없었다. 구매 패널의 목차 서너 줄이 전부였고 그마저
결과 화면까지 가야 보였다.

```
인연링크   /guide/reports · /guide/what-the-reports-contain
naminglink /guide/what-we-sell · /guide/what-you-can-buy
```

**목차와 금액을 글에 적지 않았다.** 목차는 구매 패널이 쓰는 사전 값을, 금액은
`product_settings`를 읽는다. "A4 7장"의 7도 목차 배열 길이를 센 값이라 장이 늘면 따라온다.

**한계를 함께 적었다.** 애드센스가 얄팍한 홍보 페이지를 싫어하기도 하지만, 서버가 파일을
보관하지 않는다는 것과 재발급 조건은 사기 전에 알아야 하는 조건이다. 후보 일괄 공개에는
**"광고로 여는 것과 결과가 완전히 같다"**고 적었다 — 사실이고, 적지 않으면 결제가 더 좋은
결과를 준다는 오해를 부른다.

`AI 미사용`은 넣지 않았다(사용자 결정 — 굳이 드러낼 것이 아니다).

## 7. 번역

21로케일 약관을 다시 돌렸다(문서 8개 × 21, `gpt-4o-mini`, 1달러 미만).

번역기가 괄호에 음차만 넣고 원어를 그대로 두고 있었다.

`verify-product-consistency.ts`를 새로 만든 이유가 오늘의 교훈이다. 기존 검증기는 각자의
안쪽만 본다 — 번역이 ko와 구조가 같은지, 사전 키가 다 있는지. **오늘 사고는 전부 그 사이에서
났다**: 상품표는 7장인데 고시는 3장, 약관이 파는 상품 하나를 통째로 누락, sitemap에 안내 문서
0편. 어느 것도 기존 검증기에 걸리지 않았다. 이제 셋을 대조한다 — 목차 장수 = 고시 장수
(23로케일 × 2종), 파는 상품이 약관에 있는가 + 가격 플레이스홀더 넷, 상품 코드 일치.

운영 실측:

```

inyeonlink sitemap     432 → 480 URL
```

## 9. 남은 것

### ⚠ PDF 전수 감사가 반드시 필요하다

오늘 드러난 것이 **PDF는 오류 없이 잘못 나온다**는 사실이다. 서체가 없어도 렌더는 성공하고,
글자만 빠진다. 텍스트를 추출하면 다 들어 있어 보인다. 그래서 **눈으로 보기 전에는 아무도
모른다.** 태국어·힌디어 리포트가 그렇게 한참 깨진 채였고, 아랍어는 아예 파일이 안 나오는
상태였는데 판매 전이라 드러나지 않았다.

**두 앱의 PDF 상품 전부를 로케일별로 렌더해 PNG로 확인해야 한다.** 지금 확인된 것은
인연링크 궁합 리포트뿐이다.

| 앱 | 상품 | 확인 여부 |
| --- | --- | --- |
| 인연링크 | 궁합 리포트 (7장) | ✅ 10개 문자 체계 렌더·PNG 확인 |
| 인연링크 | 인연의 결 리포트 (4장) | ❌ **미확인** |
| naminglink | 프리미엄 한자 리포트 (₩9,900) | ❌ **미확인** |
| naminglink | Korean Name Premium (US$9.99) | ❌ **미확인** |
| naminglink | Hangul Name Art (US$2.99) | ❌ 아랍어에서 죽는 것만 확인 |
| naminglink | Name Art Pack | ❌ **미확인** |

naminglink 쪽은 `pdfLocale()` 같은 장치가 아직 없다 — **아랍어·크메르어 이용자가 사면 파일을
못 받는다.** 판매 전이라 실제 피해는 없지만, 결제를 켜기 전에 인연링크와 같은 처리를 하거나
그 로케일의 구매를 막아야 한다.

감사 방법은 `apps/inyeonlink/scripts/render-report-scripts.tsx`가 본이다 — 문자 체계가 서로
다른 로케일 열 개로 렌더하고 PNG로 눈으로 본다. naminglink 상품마다 같은 스크립트가 필요하다.

### 그 밖에

- 오픈 순서는 그대로다: 실 도메인 → 애드센스 승인 → 슬롯 ID → 결제 키.
- 지금 막는 것은 우리 코드가 아니다 — 토스페이먼츠 심사 중(1달 이상 소요 가능), 페이팔 심사
  신청 후 무소식, 애드센스 심사 중, 통신판매업 미신고. `product_settings.enabled`는 넷 다
  `false`라 실제로 팔리지 않는다.
