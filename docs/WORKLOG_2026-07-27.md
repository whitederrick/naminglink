## 1. 사주 시간 보정을 IANA 진태양시로 일원화 (`9f419de`)

7/26에 "naminglink에 1987~88 서머타임 시주 오류가 남아 있다"고 적어 둔 건이다. 고치려고
열어 보니 라이브러리 보정의 결함이 하나가 아니라 셋이었다.

### 라이브러리 보정의 결함 셋

`@fullstackfamily/manseryeok`의 `applyTimeCorrection`은 이렇게 생겼다.

```js
const standardMeridian = 135;                              // 하드코딩
const longitudeCorrection = Math.round(degreesDiff * 4);   // 분 단위 반올림
calcMinute = solarMinute - longitudeCorrection;
if (calcMinute < 0) { calcMinute += 60; calcHour -= 1; }
if (calcHour < 0) { calcHour += 24; }                      // 날짜는 그대로
```

1. **표준 자오선 135° 하드코딩** — 서머타임과 과거 표준시를 통째로 놓친다. 한국은
   1948~51·1955~60·1987~88년 서머타임, 1954~61년 UTC+8:30, 1912년 이전에는 표준시
   자체가 없었다(지방 평시).
2. **날짜를 되돌리지 않는다** — `calcHour`가 음수면 `+24`만 하고 일주는 입력 날짜로 계산한다.
   서울 기준 보정은 -32분이므로 **00:00~00:32 출생자는 "전날 23:2x"라는 시각으로 당일
   일주**를 쓰게 된다.
3. **보정량을 분 단위로 반올림한다** — `Math.round(32.088) = 32`. 두 시간 경계 직전 1분
   (01:32 등)에서 반올림이 시각을 경계 너머로 밀어 시주가 한 칸 올라간다.

인연링크가 해외 출생 때문에 만든 IANA 경로(`packages/core/src/saju/timezone.ts`)에는 셋 다
없다. 그래서 **출생지를 넘기지 않은 경우에도 같은 경로를 태운다.** 기존 `timeZone`/`longitude`
인자를 그 경로의 기준점으로 쓰므로 **호출부는 한 줄도 고치지 않았다** — 네 곳 모두 이미 두
값을 넘기고 있었다.

`algorithmVersion` `naminglink-saju-v1` → `v2`. 인연링크는 점수 규칙이 그대로지만 사주 원국이
달라지는 입력이 있어 `inyeonlink-match-v5` → `v6`.

### 무엇이 얼마나 달라지는가

`packages/core/scripts/verify-korea-time.ts`가 1900~2050년 **217,440개 시각**에서 v1과 v2를
비교한다. 설명되지 않는 차이 **0건** — 모든 차이가 위 세 원인으로 갈린다.

| 사례 | v1 | v2 |

실사용자 비율로는 ②가 32/1440 ≈ 2.2%, ③이 두 시간마다 1분 ≈ 0.8%, ①은 해당 연도 출생자
전부다. 나머지는 v1과 같다.

### 함께 고친 것 — 라이브러리 날짜 표의 구멍

전수 조회하다 발견했다. **1900~2050년 55,152일 중 1956-12-31 하루가 표에서 빠져 있다**
(`Invalid solar date`로 던진다). 인연링크 궁합은 성인 생년월일을 받으므로 그날 태어난
사람에게는 **서비스가 그대로 500으로 죽는다.** 이번 변경 이전부터 있던 문제다.

또 진태양시 보정이 자정을 넘기면 1900-01-01 출생이 1899-12-31이 되어 지원 범위 아래로 나간다
(서울보다 서쪽인 인천·제주에서 실제로 발생한다).

`packages/core/src/saju/calendar.ts`를 새로 두어 둘 다 **이웃 날에서 계산해 메운다.**

- 일주는 절기와 무관한 60갑자 순환이라 하루 차이는 한 칸이다. 산술로 정확하다.
- 년주는 입춘, 월주는 입절일에만 바뀌는데 메워야 하는 날들(12/31, 1/1 언저리)은 대설~소한
  한복판이라 경계가 걸리지 않는다.
- 양쪽 이웃이 다 읽히면 **두 이웃의 년·월주가 같은지 확인한 뒤에만** 메운다. 다르면 사이에
  경계가 있다는 뜻이라 메우지 않고 원래 오류를 던진다.
- 시주는 일간에서 오자시두법으로 다시 계산한다.
- 음력 표기는 지어내지 않고 `null`로 둔다. 어차피 화면에 쓰지 않는다.

검증(`verify-calendar-gaps.ts`): 1956-12-30 일주 辛未, 1957-01-01 일주 癸酉 — 정확히 2칸
차이라 가운데 값 壬申이 유일하게 정해진다. 년·월주도 양쪽이 丙申/庚子로 같다.

## 2. 인연링크 애드센스 배너 — 다크 런치 (`d4463b6`)

퍼블리셔 ID(`NEXT_PUBLIC_ADSENSE_CLIENT`)가 없으면 **광고 스크립트도, `/ads.txt`도, CSP
완화도 붙지 않는다.** 애드센스는 심사를 통과해야 ID가 나오는데 심사는 사이트가 이미 떠 있고
방침 페이지가 갖춰져 있어야 신청할 수 있어서, 코드를 먼저 넣고 ID를 나중에 꽂는 순서가 된다.
포트원 채널 키와 같은 방식이다.

### CSP를 광고 스위치에 묶었다

애드센스는 **CSP를 공식 지원하지 않는다.** 광고 소재가 임의의 CDN에서 오기 때문에 `img-src`는
`https:` 전체를 열어야 하고 script/frame/connect도 구글 도메인을 받아야 한다. 처음부터 조여 둔
이 앱의 CSP를 되돌리는 셈이라, 여는 범위를 `src/lib/ads.ts` 한곳에 모으고 **광고가 꺼져 있으면
광고 이전과 한 글자도 다르지 않게** 두었다.

`scripts/verify-ads-csp.ts`가 두 상태를 각각 확인한다(둘 다 ALL PASS). 실제 서버(:3099)로도
확인했다 — 꺼짐: CSP 동일 · `/ads.txt` 404 · HTML에 `adsbygoogle` 0건, 켜짐: 구글 도메인
개방 · `/ads.txt` 200 · 슬롯 렌더링.

### 로더는 next/script가 아니라 순수 `<script>`

`next/script`는 어느 전략을 골라도 실제 태그를 런타임에 주입한다. `beforeInteractive`조차
서버 HTML에는 `<link rel="preload">`와 주입 코드만 남고 구글이 안내한 스니펫은 없다. 애드센스
심사는 그 스니펫을 찾는 절차라 형태를 맞췄다. React 19가 `async` 스크립트를 `<head>`로
올려 주므로 위치까지 안내와 같아진다(서버 HTML에서 확인).

### 광고 자리 둘

- **결과 화면** — `MatchResultView`의 *결과가 실제로 나온* 갈래 안쪽. 페이지 쪽에 두면 입력을
  못 읽어 오류가 뜬 화면에도 광고가 실리는데 내용 없는 화면의 광고는 정책 위반이다.
- **입력 화면** — 맨 아래. 제출 버튼 근처는 오클릭이 나고 그건 계정 정지 사유다.
- **랜딩은 뺐다** — 히어로가 `lg:h-[100svh]` 한 화면이라 자리가 없고, 내용이 얇은 화면의
  광고는 심사에서도 불리하다.

슬롯 ID는 자리마다 따로 받는다(`..._SLOT_RESULT`, `..._SLOT_FORM`). 비어 있으면 그 자리만
렌더링하지 않으므로 한 자리씩 켜 볼 수 있다.

### 방침 4항이 광고 스위치를 따라간다

문구를 하나로 고정하면 둘 중 한 상태에서 방침이 사실과 어긋난다 — 광고가 없는데 "게재합니다"라
적거나, 이미 싣고 있는데 "향후 게재하는 경우"라 적게 된다. `adsEnabled`를 따라가게 했다.

켜진 문구에는 애드센스가 요구하는 고지를 넣었다: 제3자 쿠키, 방문 기록 기반 게재,
`google.com/settings/ads`·`aboutads.info/choices` 해제 경로, EEA·영국·스위스 동의.
