## 왜 동결하는가

내가 고치고, 내가 검사기를 쓰고, 그 검사기가 내 사각지대를 초록불로 덮는 일이 세 번 났다.

> `verify-legal-source.ts` §④ 는 "파일 봉인과 DB 봉인의 해시가 **다르다**"를 배선의 증거로
> 삼았다. 그 갈라짐이 바로 P0-1 결함이다. **검사기가 결함을 기능이라고 증명했다.**

## 분류 기준을 고쳐 적는다

갈라야 할 선은 「제품 코드 대 시험 코드」가 아니라 **「배포 경로에 있는가」**였다.
봉인 생성 로직은 런타임 게시 관문이 읽는 값을 만든다. "제품 코드 결함 0건" 은 철회한다.

## P0-1 · 승인하지 않은 DB 약관이 봉인을 통과한다

- 자리: `scripts/seal-locale-review.ts` `buildSeal()`
- 재현: Codex

manifest 는 **파일 내용**을 승인했는데 resolver 가 **DB 내용**을 골라 오면, 둘이 같은지
확인하지 않고 봉인한다. 드리프트 검사는 파일 인벤토리만 본다.

```
관측: skipped = []   ·   봉인된 문서 4건   ·   ko:<kind> 봉인값 = 바뀐 DB 내용의 해시
```

### 합격 조건 — 양방향

```
① 승인한 적 없는 DB 내용 → 봉인하지 않는다
② 정상 승인한 DB 내용     → 봉인한다. 막지 않는다
③ 불일치 시 부분 봉인을 쓰지 않고 전체 작업이 비정상 종료한다
```

③이 핵심이다. **호출자가 무시할 수 있는 반환값은 관문이 아니다.** `skipped` 만 돌려주면
부르는 쪽이 그냥 넘어갈 수 있다.

②가 빠지면 `verify-legal-source` 를 영구 차단으로 만들었던 실수를 반복한다.

### 범위 — packet 제외 선언과의 충돌을 닫는다

Codex 지적: P0-1 계약은 packet 을 포함하라 하고, 「범위 밖」은 packet 발급을 제외했다.
그리고 manifest 검증이 파일 기반 `scopeInventory()` 를 쓰므로, **DB 기준으로 정상 승인한
manifest 를 만들면 오히려 파일 드리프트로 거부된다** — ②를 시험할 방법 자체가 없었다.

좁혀 적는다.

> **실제 packet 발급은 하지 않는다.** 다만 packet 과 봉인이 공통으로 쓸
> **법률 원본 → artifact 변환 함수**까지는 이번 수정 범위에 포함한다.
> **DB 기준 synthetic manifest 의 정상 승인 시험(②)까지 수행한다.**

### 계약

manifest 의 `targetHash` · DB→파일 원본 선택 · 봉인이 **모두 같은 최종 문서**를 가리킨다.

## P0-2 · 임의의 `reviewSourceHash` 가 유효한 증빙으로 통과한다

- 자리: `scripts/locale-manifest.ts:171` 부근 · `scripts/regeneration-guard.ts:86`
- 재현: Codex → Claude App 이 코드로 확인

검사가 **구조뿐**이다 — `origin` 엔 없어야, `translated` 엔 있어야. **값이 실제 원문과 맞는지는
아무도 보지 않는다.** 게다가 `regeneration-guard.ts:86` 이 그 값을 **드리프트 비교의 기준**으로
쓴다. 위조값이면 기준 자체가 쓰레기다.

```
reviewSourceHash: "bogus" · sourceKind: "translated"
→ validateManifest / sourceKindErrors / inventoryVersionErrors 모두 0건 · scopeComplete true
```

### 「실제 기준 원문」의 정의 — artifact 단위 규칙

Codex 지적: 1판은 "재계산하라"만 있고 **무엇에서** 계산할지가 없었다. `en` docs 에는 사람이
쓴 원문과 `--fill-en` 산출물이 섞여 있어 **로케일 단위 규칙으로는 계산할 수 없다.**

최종 합의의 artifact 별 규칙을 여기로 옮긴다.

| artifact | sourceKind | reviewSourceHash |
|---|---|---|
| `en` docs 직접 작성 | `origin` | 없음 |
| `en` docs 의 `--fill-en` 산출물 | `translated` | 대응하는 `ko` artifact 해시 |
| 비영어 docs | `translated` | 대응하는 `en` artifact 해시 |
| `ko` legal | `origin` | 없음 |
| 비한국어 legal | `translated` | 대응하는 `ko` artifact 해시 |
| screen · consent **전체 로케일** | `origin` | 없음 |

`screen` · `consent` 는 **생성기 없는 직접 작성물**이므로 로케일을 가리지 않고 `origin` 이다.
2판은 "screen · consent 원문"이라고만 적어 어느 로케일까지인지 다시 해석이 갈릴 수 있었다.

**예외 하나** — 사람이 다른 원문과 대조했다고 **명시한** artifact 만 `translated` 로 적고
실제 원문 해시를 쓴다. 명시가 없으면 `origin` 이다.

`generationProvenance` 는 이 판정과 **분리한다.**

### 합격 조건 — 양방향

```
① 실제 기준 원문 해시와 다르면        → 거부
② 실제 원문에서 계산한 값이면          → 통과
③ 대응하는 원문 artifact 가 없으면     → 검증 실패
```

### 계약

`targetHash` 와 **같은 취급**. 구조 검사가 아니라 재계산 대조.

## P0-3 · DB 미접속·조회 오류가 「게시본 없음」이 된다

- 자리: `scripts/legal-source.ts:49` `if (!supabase) return () => null`
- 자리: `scripts/legal-source.ts:57` `if (error) return null`
- 재현: Codex → Claude App 이 코드로 확인

호출자가 **「행이 없다」와 「물어보지 못했다」를 구분할 방법이 없다.** DB 가 죽은 동안
검수하면 **파일을 봉인해 놓고 화면은 DB 를 내보낸다.**

> 이 저장소가 이미 아는 자리다 — **「못 돎은 통과가 아니다」.** 나는 그 규칙을 검증 의뢰서에
> 적어 남에게 보내면서, 같은 문서에서 내 검사기가 그것을 어기고 있었다. 더 나쁘게는
> **"여섯 다 자격증명 없이 돌았다"를 장점으로 보고**했다.

### 합격 조건 — 종료 상태까지 고정한다

```
① 자격증명 없음 · 조회 오류
   운영 원본 확인·봉인 생성 경로에서는  → CANNOT_RUN 으로 보고하고 비정상 종료
② 게시본 없음                          → 파일. 정상이고 통과.
③ ①②가 서로 다른 값으로 구분된다
④ 주입 reader 를 쓰는 순수 대조군은     → 자격증명 없이도 실행 가능(①에 해당하지 않음)
```

④가 있어야 CI 에서 대조군이 돌면서도, 운영 확인 경로가 조용히 통과하지 않는다.

### 계약

**반환 자료형이 셋을 가른다.** 조건문 추가가 아니다.
`unknown | null` 로는 「없음」과 「못 물음」을 표현할 수 없다.

## P0-4 · 스캐너에 탐지 계약이 없다

- 자리: `scripts/verify-locale-inventory.ts` `shapedTables()` · `TABLE_PATTERNS`
- 재현: A·B — Claude App (실제 파일을 심어 확인, 심은 파일은 제거함) · C — Codex

### 통과해 버린 모양 셋

```
A. 따옴표 로케일 키           "ko": {...}, "en": {...}     → 미탐지, exit 0
B. 함수 안 + 타입 없음         컴포넌트 안 const ...        → 미탐지, exit 0
C. 로케일 키 1개 + fallback    임계값 >= 2 를 피함
```

### 새는 진짜 원인 (코드 확인, 2026-08-20)

선언 모양이 아니라 **키 추출 한 줄**이다.

```
verify-locale-inventory.ts:117   /^\s{2}([A-Za-z_$][\w$-]*)\s*:/gm
                                   ↑ 들여쓰기 정확히 2칸    ↑ 따옴표 없는 키만
```

`DECL` 정규식은 **함수 안 선언도 이미 잡는다.** B 가 새는 이유는 함수 안이라서가 아니라
들여쓰기가 4칸 이상이기 때문이다. A 는 따옴표 때문이다.

**추가 발견** — `verify-locale-inventory.ts:118` 주석은 "셋 이상"인데 코드는 `>= 2` 다.
주석과 코드가 다르다.

### 왜 P0 인가 — 안전장치가 같은 사각지대를 공유한다

`inventoryVersion`(`locale-inventory.ts:278`)은 `scopeInventory` 의 잎 경로에서 파생한다.
**스캐너가 못 보는 표는 인벤토리에 없으니 버전에 영향이 0이고, 봉인도 무효화되지 않는다.**
「나중에 발견되면 검수가 무효로 잡힌다」는 보호는 스캐너가 볼 수 있는 표에만 작동한다.

### 집행 방식 — 여기서 정한다 (Codex 안 채택)

Claude App 은 임계값 3 + 정규식 유지를, Codex 는 임계값 1 + AST 를 주장했다. **Codex 로 정한다.**

```
임계값 = 1.  지원 로케일 키가 하나라도 있는 객체 리터럴은 검사 대상.
```

Claude App 의 「C 는 애초에 표가 아님」은 **합의된 결함을 조용히 범위 밖으로 옮기는 것**이다.
키 1개 + fallback 표도 사용자에게 로케일별 문구를 낸다. 3개 기준은 2개짜리도 놓친다.

```
기전 = TypeScript AST.  typescript@5.9.3 이 이미 의존성에 있다.
```

임계값 1 은 **깊이를 아는 키 추출**을 요구하는데 정규식은 중첩을 셀 수 없다. 손으로 walker 를
짜나 AST 를 쓰나 분량은 같고 AST 가 정확하다. 이것은 **일곱 번째 검사기가 아니라
`verify-locale-inventory.ts` 내부 교체**다.

```
오탐은 임계값을 높여 숨기지 않는다. EXCLUDED_TABLES 에 이유와 함께 적는다.
```

### 사각지대를 계약에 적는다 (Claude App 안 채택)

> 이 검사기는 **리터럴 로케일 키를 가진 객체 리터럴**을 탐지한다.
> 계산으로 만들어지는 표(`Object.fromEntries(LOCALES.map(...))` 등)는 **계약 밖이며
> 손으로 등록해야 한다.**

AST 도 계산된 표는 못 잡는다. 완전한 탐지기는 없다. **검사기가 자기가 못 보는 것을 말하지
않은 것**이 이 세션이 계속 실패한 자리다. 지킬 수 있는 약속으로 바꾸고 못 지키는 부분을 적는다.

### 합격 조건

```
① A·B·C 세 본문을 각각 심으면 → 인벤토리 검사 실패(exit 1), 파일:줄을 지목
② 정상 등록된 표만 있으면      → 통과(exit 0)
③ 두 관문의 역할을 각각 대조한다
     AST 검사기      → 미등록 리터럴 표를 거부한다
     inventoryVersion → 등록된 인벤토리의 증감·변경을 감지한다
④ 주석과 코드의 임계값이 일치
```

**③은 1판·2판 모두 틀렸다** (Codex 지적). "`inventoryVersion` 이 스캐너와 같은 사각지대를
공유하지 않음을 증명"은 성립하지 않는다. `inventoryVersion` 은 **등록된 인벤토리만 보므로
미등록 표를 직접 잡을 수 없다.** 두 관문은 역할이 다르지 각각을 대조해야 한다.

**계산형 표는 명시된 잔여 위험이다.** 두 관문 어느 쪽도 잡지 않는다.

## P1-5 · 게시 차단 판정식이 두 벌이다

- 자리: `src/app/api/admin/site-content/route.ts:191` · `scripts/verify-legal-publish-gate.ts:62`
- 재현: Claude App

지금은 같다. 그런데 검사기가 규칙을 **다시 적어** 놓아서, 라우트를 고쳐도 검사기는 초록불이다.

### 합격 조건

```
① 판정식이 한 모듈에서 export 되고 라우트와 검사기가 둘 다 import 한다
② 판정 함수의 행동을 양방향으로 시험한다
     봉인 == 내용    → 허용
     봉인 != 내용    → 차단
     봉인 없음       → 기존 정책 유지
```

「양쪽이 함께 바뀌는지」 대조군은 **넣지 않는다**(Claude App 지적). import 하면 두 벌이 아닌
것이 구조적으로 참이고, 거기에 시험을 더하면 「도는가만 보는 형식적 시험」이 하나 는다.
다만 판정 함수 자체의 양방향 행동 시험은 남긴다(Codex 정제).

### `stampText` 는 「못 봤음」이 아니라 「지금은 없는 게 정상」이다

`HangulStampCard` 는 **이름 도장 굿즈** 주문 카드이고, 그 상품은 **통신판매업 번호와 PG
연계가 끝나기 전까지 닫혀 있다.** `/ja/stamp-order` 는 주문 양식 대신 일시중지 안내만 낸다.

```
/ja/stamp-order  200
  "現在、名前はんこのご注文は承っておりません"   ✓ 그려짐
  stampText · STAMP_MAX                          0건  ← 양식 자체가 없다
```

그래서 이 자리에서 확인할 것은 `stampText` 가 아니라 **일시중지 안내가 로케일별로 뜨는가**다.
상품이 열릴 때 `stampText` 를 확인 목록에 되살릴 것.

> **기록해 둔다.** 이 항목을 처음에 「유료 AI 호출이 필요해 못 봤다」고 적었는데 **틀린
> 이유**였다. 상품 상태를 보지 않고 원인을 지어낸 것이다. 「확인함」을 「못 봤음」으로 적는
> 것만으로는 부족하고, **왜 못 봤는지도 재야 한다.**

### 도장 상품이 열릴 때 해야 할 확인 — 지금은 못 하고, 잊으면 안 되는 것

도장 주문은 **통신판매업 번호와 PG 연계**가 끝나야 열린다. 그때까지 아래는 **확인할 수 없다.**
「검사가 통과했다」가 아니라 **「검사할 대상이 화면에 없다」**는 뜻이다.

**열리는 날 되살릴 것:**

```
□ ui-labels 의 stampText 가 HangulStampCard 에 실제로 그려지는가
    자리: src/components/HangulStampCard.tsx:116
    경로: 한글 발음(음차) 서비스 결과 화면 → HangulPronunciationResultPage 안의 주문 카드
    지금 못 보는 이유: 상품이 닫혀 있어 카드가 어느 경로로도 그려지지 않는다
    확인 방법: 결과를 만들어야 도달한다(유료 AI 호출). 열릴 때 함께 확인할 것.

□ 완료 조건의 「6개 라벨」 목록에서 stampText 를 **다시 확인 대상으로** 되돌릴 것
    지금은 「지금은 화면에 없다」로 빠져 있다. 상품이 열리면 이 예외가 근거를 잃는다.

□ stamp-order 화면이 안내에서 **주문 양식으로** 바뀌는가
    자리: src/app/[locale]/stamp-order/page.tsx:108
    지금은 stampPausedNotice 만 낸다(로케일별 문구 23벌).
    열리면 그 안내가 사라져야 하고, 사라졌는지 눈으로 봐야 한다.

□ 열린 뒤 stampPausedNotice 를 지울지 남길지 정할 것
    남긴다면 **일시중지 상태를 다시 켜는 스위치**가 무엇인지 함께 적을 것.
    지금은 화면이 항상 안내를 내므로 스위치가 코드 수정이다.
```

**지금 확인해 둔 것(2026-08-20):** `/ja/stamp-order` 는 200 이고 일시중지 안내가 ja 로
그려진다. 주문 양식(`stampText`·`STAMP_MAX`)은 **0건** — 닫힌 상태가 화면에 반영돼 있다.

> **이 절을 지우지 말 것.** 상품이 열리는 날 이 목록이 없으면, `stampText` 는 「이미 확인한
> 것」으로 남은 채 아무도 안 본 문구가 화면에 나간다. 검수 구조가 막으려는 바로 그 모양이다.

### 인벤토리 수치

`2a779d6` 기준선은 화면 357 · 문서 199 · 법률 115 · 결제 고시 34 = **705/로케일**이다.
**영구 계약이 아니다.** 정상적으로 등록된 문구가 늘면 숫자는 바뀐다. 수정 전후 비교용
기준선으로만 쓴다.

### 대조군

**이번에 실제로 통과했던 본문을 그대로 넣는다.**

**정정 (1판 오류)** — 1판은 "가짜 이름이 242→323→357 의 원인"이라고 적었다. 사실이 아니다.

못했을 뿐**이다. 원인과 미탐지는 다르다.
