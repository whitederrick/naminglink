## 1. 먼저 정리해 둘 것 — 두 서비스가 파는 방식이 다르다

이 문서를 읽다 헷갈리기 쉬운 자리라 앞에 적는다. **무엇을 팔고 있는가가 서비스마다 다르고,
그래서 "무엇이 새면 안 되는가"도 다르다.**

| | 무료 화면 | 유료 | 파는 것 |
| --- | --- | --- | --- |
| **naminglink 한자** | 후보 5개(1개 공개 + 광고로 4개) | 5개 또는 10개 | **후보 수 + 상세 해설** |
| **인연링크** | 유형 3개 · 띠 3개 | 유형 10개 · 띠 12개 | **개수 차이 그 자체** |

naminglink 한자 상품 3종은 후보 수와 딸린 것이 층층이 다르다.

| 코드 | 후보 수 | 사주 해석 | PDF |
| --- | --- | --- | --- |
| `FIVE_DETAIL` | 5 | ✗ | ✗ |
| `TEN_DETAIL` | 10 | ✗ | ✓ |
| `TEN_SAJU_PDF` | 10 | ✓ | ✓ |

**결제하면 화면에도 10개가 열린다.** PDF 전용이 아니다 — 같은 `candidateLimit` 값 하나가
화면과 PDF 양쪽을 정한다(`HanjaMeaningResultPage.tsx:153`, `premium-hanja-analysis.ts:488`).

인연링크는 반대다. **화면과 PDF의 개수가 다른 것이 상품의 전부**다. 코드가 그렇게 적어 두었다 —
"화면보다 더 주는 것이 있어야 판다"(`affinity-report.tsx:29`).

## 2. naminglink — 잠금이 화면에만 있었다 (`9c9d8f0`)

### 무엇이 새고 있었나

```
ResultCard.tsx   const locked = index >= revealedCount
```

잠금 판정이 이 한 줄뿐이었다. **잠긴 후보가 이미 평문으로 브라우저에 내려와 있어**
개발자도구를 열거나 `sessionStorage`를 덤프하면 광고도 결제도 없이 다 읽혔다.

파고 보니 새는 것이 광고만이 아니었다. **프리미엄 상세로 파는 6~10번 후보도 같은 평문에**
들어 있었다. 결제 패널이 하는 일이 화면 숫자를 5에서 10으로 올리는 것뿐이라, 그 후보들은
결제 없이도 처음부터 손에 있었다. 광고 우회가 아니라 **결제 우회**다.

### 왜 미뤄져 있었나, 그리고 어떻게 풀었나

2026-07-22 기록에 이유가 남아 있다. 서버가 잠금을 판정하려면 "누구의 어떤 결과가 열렸는지"를
알아야 하고, 그러려면 결과를 저장해야 한다. 그런데 이 서비스는 **비회원 결과 미저장**을 팔고
있다. 원칙과 정면으로 부딪혀 보류돼 있었다.

**저장하지 않고 하는 길이 있었다.** 잠긴 내용을 암호문으로 만들어 이용자에게 맡겨 두고,
열 때 서버가 풀어 준다. 서버에는 키 말고 아무것도 남지 않는다.

```
lib/result-seal.ts          봉인·해제(server-only) · AES-256-GCM · RESULT_SEAL_SECRET
lib/candidate-seal.ts       잠긴 자리의 모양(__locked + seal)과 화면 쪽 도구(공용)
api/candidates/unseal       광고 경로 — 하나씩
api/candidates/unseal-all   결제 경로 — 상품표 candidateLimit까지만
```

**후보 하나에 봉인 하나다.** 한 덩어리로 묶으면 한 번 풀 때 전부 열린다. "광고 1회 = 후보 1개"가
성립하려면 봉인도 후보 단위여야 한다.

### 결정 둘 (사용자)

- **한 번 연 후보는 새로고침해도 열려 있다.** 예전에는 `useState(1)`이라 새로고침하면 도로
  잠겼다. 광고를 봤는데 실수로 새로고침했다고 또 보라는 것은 설명이 안 된다. 푼 후보를
  `sessionStorage`에 되쓴다.
- **프리미엄 6~10번도 이번에 포함.** 봉인 구조는 어차피 하나라 층만 하나 더 얹으면 됐다.

### 함께 손댄 것 넷

1. **정렬을 서버로.** 잠긴 후보는 적합도가 봉인 안에 들어가 화면에서 정렬할 수 없다. 덤으로
   잠긴 후보의 적합도가 응답에서 사라진다.
2. **배열 길이는 유지.** 후보 수를 세는 코드가 전부 `candidates.length`를 본다. 잠긴 칸을 빼면
   "5개 중 1개 공개"가 "1개 중 1개 공개"가 되어 열기 패널이 통째로 사라진다.
3. **저장은 평문, 전송은 봉인.** 봉인문은 12시간 만료라 그대로 저장하면 본인 기록이 나중에
   열리지 않는다. `naming_logs`에는 평문으로 넣고 `/api/account/results/[id]`가 **읽을 때 다시
   봉인**한다. 이 재봉인을 빼면 기록 열람이 잠금 우회 뒷문이 된다.
4. **주문 하나는 결과 한 벌만 연다.** 일괄 공개 주문에 `unsealSid`를 적어 다른 결과를 만들어
   같은 주문으로 또 여는 길을 막았다. 어느 한 벌인지만 남으므로 미저장 원칙과 무관하다.

### 키가 없으면 — 조용히 넘어가지 않는다

평문 폴백은 두지 않았다. 그 폴백은 "봉인이 꺼진 채 몇 달"이 되는 길이고, 이 저장소에는
조용한 플래그(`countReviewRequired`)가 켜진 채 방치된 전례가 있다.

**키가 없으면 잠긴 후보를 아예 내려보내지 않고 운영자에게 알린다.** 무료 후보는 그대로 나가므로
서비스는 살아 있다. 그래서 배포 확인 신호가 하나 생겼다 — 응답의 후보 칸이 10이면 키가 먹은
것이고, 1이면 키가 없는 것이다.

## 3. 인연링크 — 파는 것이 무료 응답에 통째로 있었다 (`9a4e8d0`)

naminglink를 고친 뒤 **같은 유형이 더 없는지** 넓혀 본 데서 나왔다. 그리고 나왔다.

`/api/match`와 `/api/affinity`가 엔진 결과를 **통째로** 돌려주고 있었다. 그 안에는 코드가
스스로 "유료 리포트에만 쓴다"고 못 박은 값이 들어 있다.

```ts
// lib/engines/index.ts:92
/** 유료 리포트에만 쓰는 심화 자료(`./detail`).
 *  **화면은 이 값을 그리지 않는다.** */
detail: MatchDetail;
```

화면 컴포넌트에 그 필드 참조가 **0건**인데, PDF는 바로 그 값들로 4~6장과 부록을 만든다.
인연의 결은 더 노골적이다 — PDF가 파는 "열 유형·열두 띠 전체 순위표"가 무료 응답에 그대로
실려 나가고 있었다. 화면이 `slice(0, 3)`으로 셋만 그릴 뿐이었다.

**naminglink보다 뼈아픈 자리다.** 그쪽은 잠금 UI라도 있었고, 여기는 그것조차 없다. 그리고
인연링크가 파는 것은 PDF 하나뿐이라, 이 누수는 상품의 존재 이유가 통째로 나가는 것이었다.

### 고치기는 오히려 쉬웠다

PDF 발급 라우트가 **입력으로 엔진을 다시 돌린다**(`api/report/pdf/route.ts:179`). 화면이 보낸
결과를 쓰지 않으므로, 무료 응답에서 필드를 빼기만 하면 되고 PDF는 영향이 없다.

**허용목록으로 만들었다.** 뺄 것을 지우는 방식이면 나중에 유료 필드가 하나 늘 때 아무도 여기를
고치지 않고 그대로 새어 나간다.

```ts
const PAID_ONLY_READING_KEYS: Record<
  Exclude<keyof PersonReading, keyof PublicPersonReading>, true
> = { allyRatio: true, vitality: true, /* … */ };
```

엔진에 필드가 하나 늘면 이 타입이 맞지 않아 **빌드가 깨진다** — 무료로 낼지 리포트에만 실을지
누군가 반드시 정하게 된다. 실제로 임시 필드를 끼워 넣어 깨지는 것을 확인하고 되돌렸다.

### 자르기 전에 그 배열을 읽는 곳을 전부 찾을 것

간이 유형 확인기가 `outcome.stems` 전체에서 순위를 계산하고 있었다. 목록만 잘랐다면
**대부분의 유형에 "0순위"가 나왔다.** 천간 순서만 글자로 따로 보내(`stemOrder`) 해결했다.
순위 자체는 원래 공개다 — 생년월일을 넣으면 알려 주는 팝업이라 열 번 물으면 어차피 다 나온다.
리포트가 파는 것은 순위가 아니라 항목 점수다.

## 4. 검수에서 함께 나온 결제 결함 둘

### 한 결제로 다른 사람 리포트를 다섯 번까지

주문에 입력이 남지 않고 발급 때마다 클라이언트가 생년월일을 보내는데, 재발급이 5회 허용이었다.
₩1,900을 한 번 내고 매번 **다른 두 사람**을 실어 보내면 그대로 나왔다.

첫 발급 때 **입력 지문**만 주문에 적어 그다음부터는 같은 대상만 받게 했다
(`lib/report-order-binding.ts`). 지문에서 생년월일을 되돌릴 수 없어 미저장 원칙과 부딪히지
않는다 — naminglink의 `unsealSid`와 같은 방식이다.

### 인연의 결은 국내 결제로 파일을 받을 수 없었다

토스는 서버 라우트를 거쳐 `/affinity/result`로 돌아오는데 그 주소에는 입력 프래그먼트가 없다.
궁합 화면에는 복원 처리가 있었지만 **인연의 결 화면에만 빠져 있었다.** 결제는 되고 물건은
안 나가는 자리다. 판매를 열기 전에 찾은 것이 다행이다.

## 5. TEST 채널 가드 (`b798525`)

포트원은 한 상점에 LIVE 채널과 TEST 채널이 함께 있을 수 있고, **채널 키는 브라우저에 노출된다.**
그래서 "LIVE 채널인가"를 서버가 확인하지 않으면 누구든 실제 돈 없이 결제를 성사시킨다.

`PORTONE_ALLOW_TEST_CHANNEL`은 그 검사를 다크 런치 기간에만 끄려고 둔 값인데 환경 가드가 없어,
**운영에 켜진 채 남으면 그대로 구멍**이었다. 지우기를 사람이 기억하는 방식이다.

`isDevEnvironment()`를 한 겹 얹었다. `VERCEL_ENV=production`이면 어떤 설정으로도 개발이 되지
않으므로 값이 남아 있어도 사고가 나지 않는다.

**두 앱을 함께 고쳤다.** `lib/portone.ts` 첫머리가 "검증 규칙이 갈리면 한쪽에만 구멍이 생긴다,
한쪽만 고치지 말 것"이라고 적어 둔 자리다.

**잃는 것 하나**: 운영 도메인에서 테스트 채널로 결제해 보는 흐름이 막힌다. 실채널 배선을 미리
확인하려면 **Preview 배포에 `APP_ENV=dev`**를 넣고 거기서 한다.

## 6. 검증

계산을 건드리지 않았다는 것부터, 실제 서비스가 그렇게 동작한다는 것까지 순서대로 확인했다.

| 무엇 | 결과 |
| --- | --- |
| `verify-candidate-seal.ts` (신규 26항목) | 변조·만료·다른 키·결과 섞기·키 없음 전부 거절 |
| `verify-public-outcome.ts` (신규 27항목) | 유료 필드 부재 + 자른 순서가 원본과 일치 |
| `verify-test-channel-guard.ts` (신규, 환경 7조합 × 2앱) | 운영에서 플래그가 켜져 있어도 차단 |
| 인연링크 엔진 회귀 스냅샷 | **베이스라인과 변동 없음** |
| 기존 검사 전부 | 격리 스윕(494파일)·앱 분리·상품 일관성·i18n·광고 CSP 통과 |
| 화면 | 광고로 열기 → 되쓰기 → 새로고침 유지 → 실패 문구까지 실제 클릭 |
| 확인기 팝업 | **9순위** 표시 = 서버 기대값 9 (구 코드로는 `0`) |
| PDF | 표본 렌더 4장·순위 1~12·띠 12종 전부 남아 있음 |
| 실 서비스 | naming-link.com·inyeonlink.vercel.app 17항목 전부 통과 |

### 검증이 잡아낸 실제 회귀

**봉인을 넣자 유료 상품이 조용히 줄어들었다.** 화면의 결과를 서버로 되보내는 자리(유료 리포트
주문·운영자 테스트)가 봉인문을 그대로 넘기고 있어, 잠긴 후보가 산출물에서 통째로 빠졌다.

```
한글 아트 PDF   봉인문 없이 주문 → 2장
                봉인문 함께     → 4장
```

**4장짜리 상품이 2장으로 나갈 뻔했다.** 해당 자리 셋을 전부 고쳤다.

### 검증 못 한 것 하나

**저장 기록 재봉인**(`/api/account/results/[id]`)은 로그인 계정과 저장된 이력이 있어야 태울 수
있어 확인하지 못했다. 봉인 함수는 단위 검사로 덮었고 호출은 한 줄이라 위험은 낮지만,
미검증이라는 사실은 남는다. 계정 하나로 결과를 저장한 뒤 "저장 결과 열기"를 눌러 잠긴 후보가
잠긴 채로 나오면 정상이다.

## 7. 지금 남아 있는 구멍

`/api/candidates/unseal`을 스크립트로 반복 호출하는 것은 아직 막지 못한다(시간당 60회 제한만
있다). 다만 성질이 달라졌다 — **요청 없이 조용히 읽히던 것이 요청을 남기고 세어지고 제한되는
일**이 됐고, GAM 보상형 SSV를 붙일 자리는 그 라우트 **한 곳**뿐이다.

덧붙여 AI 원가는 생성 시점에 이미 쓴 뒤라, 이 누수는 비용이 아니라 광고·결제 수익 문제다.

## 8. 배포

`RESULT_SEAL_SECRET`을 Vercel(Production·Preview)에 등록한 뒤 푸시했다. 순서가 중요하다 —
서버 환경변수는 새 배포부터 반영되므로 먼저 넣어야 그 배포가 값을 갖고 시작한다.

두 앱 배포 후 실 주소로 확인했다(§6 마지막 줄). `result-seal-unconfigured` 알림은 오지 않았다.

---

## 9. 내일 이어서 할 일

우선순위대로 적는다. **조건이 없는 것부터** — 조건이 붙은 일은 아래 §9-3에 따로 모았다.

### 9-1. 오늘 못 한 검증 하나 (5분)

**저장 기록 재봉인 확인.** 이번 변경에서 유일하게 태워 보지 못한 경로다.

```
1. 아무 계정으로 로그인해 한자 결과를 하나 만들고 "결과 저장"을 켠다
2. 계정 화면 → 저장 결과 → "열기"
3. 잠긴 후보가 **잠긴 채로** 나오면 정상
```

전부 열려 보이면 `/api/account/results/[id]`의 재봉인이 안 먹은 것이고, 그때는 기록 열람이
잠금 우회 뒷문이 된다. 위험은 낮다고 보지만(호출 한 줄) 확인은 안 된 상태다.

### 9-2. 리드타임이 있는 것 — 걸어두기만 해도 하루를 번다

내가 할 수 없고 **사람이 신청해야** 진행되는 것들이다. 오래 걸리므로 먼저 건다.

| 항목 | 왜 지금 |
| --- | --- |
| **통신판매업 신고** | 발급까지 며칠. 오픈 자체를 막는 둘 중 하나 |
| **토스페이먼츠 키 발급** | 이게 와야 실주문 검증 → 테스트채널 정리 → CSP가 도미노로 풀린다 |
| **인연링크 도메인 구매·연결** | 애드센스는 **사이트 단위 승인**이라, 도메인 없이 심사를 넣으면 오픈 직후 재심사를 다시 받는다 |

세 번째가 제일 조용하지만 제일 되돌리기 어렵다. naminglink는 이미 실 도메인으로 심사 중인데
인연링크만 `inyeonlink.vercel.app`으로 떠 있다.

### 9-3. 조건이 풀리면 바로

| 항목 | 조건 | 메모 |
| --- | --- | --- |
| 인연링크 SEO | 도메인 연결 직후 | naminglink에 sitemap·canonical·hreflang·경로 URL 패턴이 다 있다. 베끼는 작업이라 싸고, **연결 직후에 해야** 색인이 처음부터 옳은 주소로 잡힌다 |
| 실주문 결제→생성 검증 | 결제 키 | **ar 로케일 한 건 필수** — 한글 아트 PDF의 영어 번역 경로(`hangul-art-translate.ts`)가 결제 후에만 돈다 |
| 테스트 채널 흔적 정리 | 실채널 전환 | `PORTONE_ALLOW_TEST_CHANNEL` 값 삭제·웹훅 시크릿 교체·테스트 데이터 삭제·지표 초기화 |
| 엄격 CSP(nonce) | 실결제 한 바퀴 후 | 지금 켜면 결제·광고 SDK가 인라인에 의존해 **결제가 막히는 사고**가 날 수 있고 실거래 전에는 감지도 못 한다 |
| GAM 보상형 SSV | 보상형 슬롯이 붙은 뒤 | 붙일 자리는 `/api/candidates/unseal` **한 곳**뿐이다(§7) |

### 9-4. 급하지 않지만 해 두면 좋은 것

- **잔재 환경변수 5개 삭제**(naminglink). 코드가 이미 무시하므로 동작에는 영향이 없다.
  `NEXT_PUBLIC_PORTONE_CHANNEL_KEY`, `..._KAKAOPAY`(2026-07-29 결제 일원화로 제거),
  `NEXT_PUBLIC_ADSENSE_SLOT_ANALYSIS_WAIT`, `..._CANDIDATE_UNLOCK`,
  `..._HANGUL_CANDIDATE_UNLOCK`(관문에서 애드센스를 걷어내며 제거).
- **`AdRewardGate` export 정리**(인연링크). 아무 데도 임포트되지 않는 죽은 코드다. 실제로
  쓰이는 것은 같은 파일의 `AdWatchOverlay`뿐이다.
- **정기 업데이트 리듬.** 애드센스 항목 중 유일하게 "앞으로"로 남은 칸이다. 한 번의 작업이
  아니라 습관이라, 올릴 값어치가 있는 것이 생길 때 공지에 올리면 된다.
- **naminglink 재분석 횟수 게이트.** `sessionStorage`에만 있어 지우면 다시 공짜다. 알려진
  절충이지만(코드 주석에 사연이 있다) **이건 우회하면 AI 비용이 실제로 나간다.** 지금은 무료
  한도(IP당 100·전역 30,000)가 상한을 잡고 있어 급하지 않다. GAM SSV를 붙일 때 후보 열기와
  **같이** 손보는 것이 자연스럽다.

## 10. 운영에서 잊으면 안 되는 것

이번 작업으로 **새로 생긴 운영 지식**을 앞에 두고, 기존에 있던 것 중 함께 기억해야 할 것을
뒤에 붙인다.

### 10-1. `RESULT_SEAL_SECRET` — 이번에 생긴 필수 환경변수

| | |
| --- | --- |
| 어디에 | **naminglink 프로젝트만.** 인연링크는 이 변수를 읽는 코드가 없다 |
| 없으면 | 잠긴 후보를 아예 안 내려보낸다 → **화면에 후보 1개만** 보이고 열기 패널이 사라진다 |
| 판별법 | 응답의 후보 칸이 **10이면 정상, 1이면 키 없음** |
| 값을 바꾸면 | 그 전에 만들어진 결과의 잠긴 후보는 열리지 않는다(어차피 12시간 만료라 곧 사라진다) |
| Production ≠ Preview | 서로 다른 값이어도 된다. 한쪽 봉인문이 다른 쪽에서 안 열릴 뿐이고 그게 정상이다 |

**배포 순서를 지킬 것.** 서버 환경변수는 **새 배포부터** 반영된다. 값을 먼저 넣고 그다음에
푸시해야 그 배포가 값을 갖고 시작한다. 반대로 하면 그 사이 후보 1개짜리 화면이 라이브에 걸린다.

### 10-2. 운영 알림은 실패를 조용히 삼킨다

- 받는 곳: `OPS_ALERT_EMAIL`, 비어 있으면 `lib/company.ts`의 고객센터 메일
- 보내는 곳: `OPS_ALERT_FROM`, 비어 있으면 `alerts@naming-link.com`
- **발송 실패는 조용히 넘어간다.** 알림 때문에 이용자 요청이 느려지면 안 되기 때문이다.
  따라서 **"메일이 안 왔다 = 사건이 없었다"가 아니다.** 확실히 보려면 Resend 대시보드의 발송
  기록을 본다.
- 같은 사건은 5분에 한 번만 간다(인스턴스별로 세므로 완벽한 억제는 아니다).
- 웹훅·메일이 다 실패해도 **로그 한 줄은 항상 남는다** — Vercel 로그에서 `[ops-alert:` 로 찾는다.

### 10-3. TEST 채널은 운영에서 자동으로 막힌다

`PORTONE_ALLOW_TEST_CHANNEL`이 켜진 채 남아 있어도 운영 배포에서는 무시된다
(`isDevEnvironment()` 가드). **그래서 실채널 배선을 미리 확인하려면 운영 도메인이 아니라
Preview 배포에 `APP_ENV=dev`를 넣고 거기서 해야 한다.**

값 자체를 지우는 것은 여전히 체크리스트에 있지만, 이제는 사고 방지가 아니라 "안 쓰는 스위치를
남기지 않는다"는 정리 차원이다.

### 10-4. 결제 키가 와도 상품이 자동으로 켜지지 않는다

**살 수 있으려면 둘 다 필요하다** — 상품 `enabled` AND 결제 키. 지금은 상품 20건이 전부 판매
중지 상태다(2026-07-29에 내림). 키를 넣었다고 버튼이 열리지 않으니 **관리자 화면에서 상품을
켜는 단계**를 잊지 말 것. 반대로 키 없이 켜 두면 죽은 구매 버튼이 된다.

### 10-5. 두 앱의 결제 검증은 일부러 복사돼 있다

`lib/portone.ts` 첫머리에 적혀 있다 — "검증 규칙이 갈리면 한쪽에만 구멍이 생긴다,
**한쪽만 고치지 말 것.**" 실결제로 양쪽을 확인한 뒤에 `packages/core`로 합치는 것이 순서다.

### 10-6. 지표 초기화 시점

AI 사용량·글로벌 접속/활용·광고 3종은 **광고가 실제로 붙는 시점에** 0으로 되돌린다.
주문·상품 설정은 건드리지 않는다.
