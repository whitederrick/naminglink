## 1. PR #5 — 열고, 검토받고, 여섯을 닫았다

### 1.1 검토에서 나온 것

내가 쓴 코드라 독립 판정은 아니지만, **내가 놓쳤을 자리를 찾는 눈으로** 다시 읽었다.
사용자가 두 검토자(Codex · Claude App)에게도 같은 PR 을 냈다. 결론은 **여섯이 기능 결함**.

| 갈래 | 무엇이었나 |
| --- | --- |
| 정상 주소 거부 | `/a%20b` · `/100%` · `/a%b` 가 `null` 이었다. 푼 값에 공백류 검사를 걸고, 풀리지 않으면 곧바로 거부했다 |
| 조각(#) | `withReturnTo("/ko/about#help", …)` → `/ko/about#help?returnTo=…` — 쿼리가 통째로 **조각의 일부**가 되어 아무도 못 읽었다 |
| 출처가 한 칸만 감 | 안내 허브 → 안내 문서로 들어가면 `returnTo` 가 사라졌다 |
| 로그인 복귀 | `NamingForm` · `PolicyLayout` · OTP 완료 주소에서 끊겼다 |
| 자기 링크 | `/ko/about` 에서 「소개」를 누르면 `returnTo` 가 자기 자신이 됐다 |
| 물려받은 이름 | `origins[from]` 이 `toString`·`__proto__` 등을 값처럼 통과시켰다 — **네 앱 모두** |

**여섯 다 고치기 전에 시험을 걸어 빨간불을 확인했다.** 마지막 것은 특히 아프다 —
표를 **만드는 쪽**은 2026-08-20 에 Map 으로 고쳤는데 **읽는 쪽이 남아 있었다.**
「같은 결함이 네 앱에 있는지 세라」(§5)는 지켰는데, **같은 결함이 같은 앱의 반대편에 있는지**는
안 셌다.

### 1.2 판정을 하나 뒤집었다

「깨진 퍼센트」(`/%zz`)는 막는 칸에 있었다. 그런데 `/100%` 와 같은 갈래다 — 풀리지 않을 뿐
우리 경로이고 남의 사이트가 될 길이 없다. **통과 칸으로 옮겼다.**
「정상 인코딩 URL 을 거부하지 않는다」와 「깨진 퍼센트를 막는다」가 양립하지 않았고,
**막는 쪽으로 틀린 것**이라고 판단했다.

### 1.3 범위에서 뺀 것

`AccountDeletePanel` — 계정 삭제 확인 뒤 홈으로 보내는 파괴적 흐름이라 로그인 복귀와 목적이
다르다. 사용자가 그렇게 그었고 그대로 따랐다.

## 2. Supabase 리다이렉트 허용 목록 — 설정을 대조했다

`AuthPanel` 의 `emailRedirectTo` 에 쿼리를 붙였으므로 허용 목록을 확인해야 했다.

```
Site URL        https://naming-link.com
Redirect URLs   https://naming-link.com/**        (1건)
```

Supabase 문서가 안내하는 패턴 시험 도구로 대조했다.

```
✓  https://naming-link.com/en/account                                    ← 대조군(지금 동작)
✓  https://naming-link.com/en/account?returnTo=%2Fko%2Fabout             ← 이번 변경
✓  https://naming-link.com/ko/account?returnTo=%2F…%2Fresult%3Fid%3Dabcdef
✗  https://evil.com/en/account                                           ← 대조군(막혀야 하는 것)
```

**`https://naming-link.com/**` 규칙이 유지돼야 매직링크의 `returnTo` 가 동작한다.**

**곁가지**: 허용 목록에 `localhost` 가 없다. dev 매직링크는 Site URL 로 떨어져 **운영 사이트로
간다.** 기존 문제이고 이 PR 과 무관하다 — `returnTo` 를 붙이든 안 붙이든 같다.

## 4. 운영에서 눌러 봤다 — 오늘 고친 것이 실제로 돈다

```
① 붙는다   서버 HTML  /ko/guide?from=hanja-meaning        ← 깨끗한 주소
           눌렀을 때   …&returnTo=%2Fhanja-meaning         ← 브라우저가 붙였다

② 읽는다   ?returnTo=%2F…%2Fresult%3Fid%3Dabcdef%26mode%3Dtransliteration
           → 「이전 화면으로」 /global-to-korean/result?id=abcdef&mode=transliteration
           ?id= 와 &mode= 가 그대로 보존된다 ← 처음 관찰된 증상이 닫혔다
           하위 문서(/guide/hanja-basics)에서도 읽는다

③ 막는다   ?returnTo=https://example.com → 「이용 안내」 /ko/guide (거부, 이름까지 바뀜)

④ 형제 셋  inyeon ?from=toString · saju ?from=__proto__ · dreams ?from=constructor
           셋 다 「처음으로」 /ko
```

**확인 못 한 것**: 안내 허브의 **문서 카드 클릭**이 세 번 다 안 먹었다(도구 쪽 문제로 보인다).
붙이는 쪽은 푸터 링크로, 읽는 쪽은 하위 문서로 각각 확인했으므로 **부품은 다 봤지만
그 한 경로는 눌러 보지 못했다.** 그리고 **매직링크 실발송은 안 했다.**

## 5. 광고 개방 ② — 거래 직결 문구를 세고, 읽을 수 있게 만들었다

어제 §14 에서 사용자가 멈춘 자리가 **「관문만 쌓고 정작 그 일은 한 번도 안 돌렸다」**였다.
오늘 그 일이 **처음으로** 돌 수 있는 상태가 됐다.

### 5.1 66자리

```
A. 금액        21   이용약관 §4(7문단) + 요금안내 §3·4·5·6·7
B. 환불        15   환불정책 문서 전문 7개 절
C. 결제 고시    19   DIGITAL 6항목+3문장 · MADE_TO_ORDER 7항목+3문장
D. 사업자 정보   9   + 곁가지 2 (개인정보처리방침 §8)
                ──
                66
```

**범위는 전략 문서 §3.1 ②의 정의를 그대로 썼다** — 「금액·환불·사업자 정보·결제 고시,
705개가 아니라 거래에 직결되는 소수」. 자동 추출에서 개인정보처리방침 §1·§3·§6 이 함께
걸렸는데 「address」·「email」·「payment」라는 **낱말 때문**이었고, 본문을 열어 보고 뺐다 —
정규식은 그물이지 울타리가 아니다.

**숫자에 약점이 있다.** 문단 38 + 고시 항목 19 + 필드 9 를 그냥 더한 값이라 **단위가 섞여
있다.** 약관 §4 한 문단과 `email` 필드 하나는 읽는 품이 전혀 다르다.

### 5.2 기계가 이미 보는 것은 뺐다

`verify-legal-prices` 가 DB(`product_settings`)를 진실로 삼아 금액을 매번 대조하고,
`verify-checkout-consent` 가 고시 항목 수와 강조를 센다. **그래서 사람이 볼 것은 「숫자가
맞나」가 아니라 「영어 문장이 그 조건을 오해 없이 말하는가」다.**

### 5.3 읽기 도구 한 장

사용자가 조건을 그었다 — **비공개·읽기 전용 · 검사기나 배포 관문으로 만들지 말 것 ·
C 19항목과 대응하는 B 환불 문장부터 · 항목마다 통과/수정 필요/보류 + 짧은 메모 ·
결과는 저장소용 Markdown 으로 내보낼 것 · 화면 제작을 별도 제품 작업으로 키우지 말 것.**

그대로 만들었다. 영문과 국문 원문을 문단마다 나란히 두고, 결제 고시 아래에 **같은 상품을
다루는 환불 절**을 붙였다(`DIGITAL` ↔ 환불 §1·§2·§3·§4 / `MADE_TO_ORDER` ↔ §1·§5).
**이 짝은 상품 기준으로 내가 지은 것이고 코드에 그런 연결은 없다** — 화면에도 그렇게 적었다.

저장소에는 아무것도 넣지 않았다. 검사기 0건, CI 배선 0건.
