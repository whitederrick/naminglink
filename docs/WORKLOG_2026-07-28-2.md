## 0. 이 세션에서 정한 것

### 이름 궁합은 총점에 넣지 않는다

사용자가 인연링크의 추가 서비스를 물었고, 셋을 검토했다 — 사주 궁합(기존), 이름 궁합,
"나에게 맞는 상대". **이름 궁합을 총점에 섞지 않기로 했고, 순서를 뒤집어 "맞는 상대"를 먼저
만들었다.**

이름 궁합을 총점에서 뺀 이유 셋:

1. **근거의 강도가 다른 것을 평균하면 전체가 약한 쪽으로 내려간다.** 지금 엔진은 억부용신·
   십신 짝까지 들어간 명리 계산이고 이게 "AI가 대충 만든 것이 아니다"라는 유일한 방어막이다.
   성명학 수리는 그보다 논란이 많다. 한 숫자에 녹이면 그 숫자 전체가 획수 점수로 읽힌다
2. **사람마다 항목 수가 달라진다.** 한자를 모르는 사람이 많고 외국인은 아예 없다. 3항목으로
   계산된 점수와 2항목으로 계산된 점수는 비교할 수 없다 — 유료 상품에서 환불 사유다
   (계획서 §104가 GPT 점수를 배제한 것과 같은 이유)
3. **이름은 바꿀 수 있고 사주는 못 바꾼다.** 점수가 이름에 좌우되면 "개명하면 궁합이 오르나"가
   따라오는데, 하필 형제 서비스가 작명이다. 결과의 중립성이 무너진다

### 데이터 실측 — 성명학은 지금 못 한다

운영 DB를 직접 읽었다.

```
official_hanja_entries      9,938행
  stroke_count 채워진 행         0      ← 컬럼만 있고 전부 null
  자원오행 컬럼                  없음    ← hanja.ts에 소량 하드코딩이 전부
```

획수·자원오행 기반 성명학은 **9,938자 데이터 입력이 선행 작업**이고 출처도 명확해야 한다
(대법원 인명용한자표에는 획수가 없다). 지금 당장 가능한 유일한 근거는 **음오행**(초성 기반)
하나뿐 — 규칙이 곧 데이터라 채울 것이 없고 한글만 있으면 된다. 만든다면 무료+광고로 분리하고
사주 궁합으로 올려보내는 계단으로 쓴다.

## 1. 인연의 결 (`3ab9bdc`)

메뉴가 둘이 됐다. 랜딩에 나란히 둔다 — 채운 버튼이 `사주 궁합 보기`, 테두리 버튼이 `인연의 결`.

| | 경로 | 받는 것 |
|---|---|---|
| 사주 궁합 | `/compatibility` | 두 사람의 생년월일 |
| **인연의 결** | `/affinity` | **내 생년월일 하나** |

### 왜 이것부터 만들었나

- **새 데이터도 새 규칙도 필요 없다.** 기존 엔진을 거꾸로 돌리면 된다. 세 후보 중 유일하게
  데이터 작업이 0인 메뉴다
- **혼자서도 쓸 수 있는 유일한 상품이다.** 궁합은 상대의 생년월일을 알아야 하는데, 그걸 아는
  단계면 이미 관계가 꽤 진전된 뒤다. 짝이 없거나 생일을 모르는 사람은 이 사이트에 와서 할
  것이 없었다
- 남 이야기가 아니라 **내 이야기**라 유료화가 자연스럽다(아직 무료)

### 전수 탐색이 필요 없는 이유

사주 궁합의 네 항목이 **서로 겹치지 않는 값**을 본다.

| 항목 | 보는 것 | 후보 수 |
|---|---|---|
| 일간 관계·배우자성 | 두 사람의 **일간** | 천간 10 |
| 오행 보완 | 내 용신과 상대의 **오행 세력** | 오행 5 |
| 일지 관계 | 두 사람의 **일지** | 지지 12 |
| 띠 관계 | 두 사람의 **연지** | 지지 12 |

항목끼리 값을 주고받지 않으므로 **축마다 따로 최고점을 찾으면 그것이 곧 전체의 최고점**이다.
수백만 개의 생년월일을 돌릴 필요가 없다.

### 점수 규칙을 새로 만들지 않았다

전부 궁합 엔진 것을 불러 쓴다. 그래서 `ENGINE_VERSION`은 **v9 그대로**이고 회귀 베이스라인도
변동이 없다. `relations.ts`에서 `relationOfDayMasters`를 꺼내 놓은 것이 유일한 리팩터다 —
사람 전체가 아니라 천간 두 글자만 있으면 관계가 정해지므로, 실존하지 않는 상대에게도 같은
규칙을 쓸 수 있다.

`scripts/verify-affinity.ts`가 그 주장을 기계로 확인한다. **1등으로 꼽은 일간을 실제로 가진
날짜를 60일 안에서 찾아** `runMatch`를 돌리고 항목 점수가 같은지 대조한다.

```
3) 궁합 엔진과 같은 값을 말하는가
  PASS  丁 / 己 / 乙 / 庚 — 일간 관계·배우자성 점수가 궁합과 같다
  PASS  酉(rooster) — 띠 관계 점수가 궁합과 같다
5) 띠 → 출생 연도 환산
  PASS  1988-01-15 → 사주 연주는 1987년 (입춘 경계)
ALL PASS
```

### 총점은 내지 않는다

실제 사람은 일간과 오행 세력이 따로 놀지 않는다 — 甲木인 사람은 대개 木도 두텁다. 축을 따로
세우는 방식은 그 상관을 무시하므로 **축별 1등을 모은 "완벽한 상대"는 실존하지 않을 수 있다.**
그래서 항목 점수만 내보내고 합산은 사주 궁합에 넘긴다. 그게 정직하고, 유입 계단이기도 하다.

### 화면 — 성향이 본문, 띠는 곁들임

사용자가 고른 방향이다. 순서대로:

1. **당신의 자리** — 일간·신강신약 + 일간이 무엇인지 풀이
2. **잘 맞는 결 3** — 성향 → 행동 단서 → 십신 → 짝 설명 → 항목 점수
3. **겪어 봐야 하는 결 1** — 꼴찌 하나만. 여럿을 "피하라" 늘어놓으면 사람을 가려내는 꼴이 된다
4. **필요한 기운** — 억부용신
5. **곁들여 보는 띠** — 잘 맞는 3 / 부딪히기 쉬운 1, **출생 연도와 나이 차 포함**
6. **이 사람이 나와 맞을까** — 확인기 팝업 버튼
7. **사주 궁합으로** — 이 화면이 못 하는 총점을 하는 자리

### 알아볼 수 있게 만드는 데 대부분을 썼다

첫 판을 보고 사용자가 지적한 것이 전부 같은 문제였다 — **은유라서 눈앞의 사람에게 대 볼 수 없다.**

- **행동 단서 추가** — 천간 10종을 겉으로 드러나는 행동 3개씩으로 옮겼다. 丙(병화)이면
  "처음 보는 사람에게 먼저 말을 겁니다 / 좋고 싫음이 표정에 드러납니다 / 여럿이 모이면
  자연스럽게 가운데에 서 있습니다". **비유를 지우지 않고 아래에 쌓는다**(사용자 요구)
- **띠 → 출생 연도·나이 차** — "닭띠와 맞습니다"는 쓸 데가 없다. 남의 띠를 외우고 다니는
  사람은 없고 생년은 대개 안다. `1993년생(5살 아래)` 꼴로 바꿨다.
  **1984년이 갑자년**이라는 것 하나로 전부 계산하고, 표를 따로 두지 않는다
- **용어를 처음 나오는 자리에서 푼다** — 일간·배우자성이 설명 없이 나오고 있었다.
  `배우자성`→`배우자 자리`, `일간 관계`→`기질 맞물림`으로 라벨을 바꾸고 첫 카드에 풀이를 단다
- **일지 나열 삭제** — `寅 호랑이 · 卯 토끼 · 亥 돼지`를 보여 주고 있었는데 **동물 이름이
  거짓 신호였다.** 바로 위 띠 칸에서 같은 동물 이름을 쓰는데 일지는 태어난 해가 아니라 날에서
  나오므로 띠와 무관하다. 게다가 좋은 쪽인지 나쁜 쪽인지도 안 적혀 있었다(사용자가 되물었다)

### 입춘 경계

띠를 연도로 바꾸면서 생긴 함정이다. 사주는 새해가 아니라 **입춘에 해가 바뀐다.** 라이브러리가
숫자로 된 해를 돌려주지 않으므로, 달력 해와 그 앞 해 중 연지가 맞는 쪽을 고른다. 한 해가
어긋나면 나이 차가 전부 어긋난다. 하니스에 `1988-01-15 → 1987년(토끼띠)` 검증을 넣었다.

### 간이 확인기 (팝업)

유형 설명이 아무리 자세해도 **확정은 생일로만 된다.** 그렇다고 여기서 궁합을 다 계산하면 사주
궁합과 경계가 사라진다. 그래서 유형과 순위까지만 말한다.

- `/api/day-master` — 날짜 하나를 받아 **일간만** 돌려준다. 순위는 화면이 매긴다(유형 목록을
  이미 들고 있으므로 서버가 다시 보낼 이유가 없다)
- 출생 시각·출생지는 받지 않는다. 일주가 자정 언저리에서만 갈리므로, 다 받으면 궁합 폼과
  다를 바가 없어진다. 대신 그 한계를 화면이 밝힌다
- `LegalModal`과 같은 구조 — 바깥 눌러 닫기(`onMouseDown` 기준), Esc, 스크롤 잠금, 포털
- 버튼 색을 세 단계로 갈랐다: 확인하기(칠한 자두색) / 다른 사람 확인(테두리) / 닫기(무채색).
  앞서 확인하기와 닫기가 둘 다 칠해져 있어 무엇이 진짜 행동인지 구분되지 않았다

### AI는 쓰지 않는다

사용자가 물어 확인했다. `apps/inyeonlink`와 `packages/core` 전체에 AI 호출이 **0건**이다
(`openai|anthropic|gpt-|@ai-sdk|generateText` 스윕). 숫자는 만세력 + 규칙표에서, 문장은 고정
사전에서 나온다. 계획서가 정한 대로다 — 점수를 AI에 맡기면 재조회 때 숫자가 달라진다.

## 4. 로컬 푸터가 비어 있던 이유

사용자 신고: "푸터 정보가 로컬에서만 업데이트가 안 된다."

**`apps/inyeonlink/.env.local` 파일이 아예 없었다.** `company-server.ts`는 Supabase 클라이언트가
없으면 DB를 보지도 않고 폴백을 그린다.

```ts
const supabase = getSupabaseAdminClient();
if (!supabase) return fallbackCompanyInfo;   // 로컬은 여기서 끝
```

Next.js는 **각 앱 폴더의 `.env.local`만** 읽는다. 모노레포라도 루트나 형제 앱 것을 가져오지
않는다. 사용자가 `NEXT_PUBLIC_SUPABASE_URL`·`SUPABASE_SERVICE_ROLE_KEY` 둘을 넣어 해결했고,
푸터가 `197-86-02010`·실제 주소를 읽어 오는 것을 확인했다.

`통신판매업 신고 준비 중`은 폴백이 아니라 **DB에 실제로 들어 있는 문구**다. 신고번호가 나오면
naminglink 관리자 화면에서 한 번 고치면 두 서비스에 함께 반영된다.

DB는 다르다 — 꺼진 것은 인연링크 상품뿐이다. 다만 운영 페이지에서 토스 클라이언트 키나 포트원
채널 키 문자열이 보이지 않는다. **Vercel 환경변수에 토스 키가 있는지 확인이 필요하다** — 없는
상태로 상품이 켜져 있으면 눌러도 아무 일 없는 구매 버튼이 노출 중이다.

### 애드센스 준비 점검 — 코드는 통과, 도메인이 막고 있다

`verify-ads-csp.ts`를 껐을 때와 켰을 때 양쪽으로 돌려 전부 PASS. `/ads.txt`도 정상(지금은 404,
ID를 넣으면 정상 발급). 방침 광고 조항도 `adsEnabled`를 따라간다. **ID만 꽂으면 열린다.**

그런데 점검 중 더 큰 것을 찾았다. 구글 공개 DNS(8.8.8.8) 직접 조회 결과:

```
naming-link.com     NS → 없음    A → 없음
inyeon-link.com     NS → 없음    A → 없음
inyeonlink.vercel.app          → 216.198.79.195  ✓
```

**두 도메인 모두 네임서버조차 위임되지 않았다.** 지금 두 서비스 다 `*.vercel.app`으로만 떠 있다.

- 애드센스는 `*.vercel.app`으로 **심사 신청이 안 된다.** 본인 소유 도메인이어야 하고 `ads.txt`를
  루트 도메인에 둘 수 있어야 한다
- 토스 가맹 심사도 사이트 URL 단위다. **토스에 어떤 URL로 신청했는지 확인이 필요하다**

즉 **도메인 연결이 결제와 광고 양쪽의 공통 선행 조건**이다.

### 결정 — 인연의 결은 무료 유지 + PDF만 판다

화면을 유료로 막으면 **혼자서도 쓸 수 있는 진입점**이라는 이 메뉴의 존재 이유가 사라진다.
값은 궁합 리포트와 같은 ₩990 / US$1.99(사용자 확정) — 분량이 비슷한데 값이 다르면 "왜 이건
비싼가"를 설명해야 한다.

### PDF는 4장이다 (3장으로 잡았다가 늘렸다)

```
1장  표지 + 당신의 자리      2장  잘 맞는 결 셋
3장  겪어 봐야 하는 결 + 천간 전체 순위표      4장  띠 전체 순위표(연도·나이 차)
```

**화면보다 더 주는 것이 있어야 판다** — 화면은 상위 셋만 보여 주지만 PDF는 천간 열 종과 띠
열둘을 전부 싣는다. 궁합 리포트가 화면에 없는 오행 세력 수치를 담는 것과 같은 규칙이다.

셋으로 밀어 넣었더니 "겪어 봐야 하는 결" 제목만 앞 장 끝에 남고 카드가 다음 장으로 넘어가
**오히려 다섯 장**이 됐다. `render-affinity-sample.tsx`로 만들어 **PNG로 렌더해 보고 알았다** —
텍스트 추출로는 안 보이는 종류다. 함께 잡은 것:

- 표 마지막 행이 푸터를 덮고 있었다 → 아래 여백 56→72, 표 행에 `wrap={false}`
- 열 이름 자리에 섹션 제목을 돌려쓰고 있었다 → `#·유형·기질 맞물림·배우자 자리`
- 사전·상품정보 고시의 "3장"을 전부 4장으로. **표시와 실물이 어긋나면 전자상거래법 문제다**

### 구조는 넓히기만 하고 복사하지 않았다

- `report-product.ts` — 상품을 **종류×권역 2차원**으로. 주문 종류(`orderType`)도 여기서 정한다
- 주문·발급 라우트에 `kind`. 발급은 **판별 합집합**이라 인연의 결 주문에 두 사람 입력을 실어
  보내는 요청이 통과하지 못한다. 주문 조회도 종류까지 맞춘다
- 토스 승인 라우트가 두 상품을 다룬다. **주문에 적힌 종류를 믿고** 돌아갈 화면을 정한다 —
  쿼리의 `kind`는 결제창을 거치며 손댈 수 있어 주문을 찾은 뒤에는 쓰지 않는다
- 구매 패널 하나가 둘을 그린다. 복사하면 청약철회 동의 같은 법 처리가 두 벌이 된다
- **`warmUpLayoutEngine`을 공용으로 뺐다.** 한 프로세스의 첫 렌더가 이후 모든 문서의 줄바꿈을
  정하는 라이브러리 버그 회피책인데, 새 리포트에서 빠뜨리면 그 상품만 깨진 영문을 내보낸다.
  샘플 스크립트가 한국어를 먼저 렌더하게 두어 예열이 깨지면 바로 드러나게 했다

### 상품표 현황

```
 -- AFFINITY_PDF_KRW  KRW  990     -- GUNGHAP_PDF_KRW  KRW  990
 -- AFFINITY_PDF_USD  USD  199     -- GUNGHAP_PDF_USD  USD  199
```

넷 다 꺼져 있다(정상). 토스·페이팔 키 등록 후 naminglink 관리자 화면에서 켠다.
