## 1. 결제 구조가 바뀌었다 (가장 큰 변화)

**사용자 확정: 국내는 토스페이먼츠 직접 연동, 해외는 포트원 경유 페이팔.** 두 앱 모두 같다.
포트원 카카오페이 심사는 취소 요청, 포트원 토스는 이미 취소, 페이팔은 진행 중.

이 결정으로 오전에 붙였던 포트원 카카오페이 테스트 채널은 **국내 결제의 최종 경로가 아니게
됐다.** 다만 토스 키가 없으면 포트원으로 떨어지도록 해 두어 지금 동작에는 영향이 없다.

### 포트원과 토스는 흐름이 반대다

| | 포트원 | 토스페이먼츠 |
|---|---|---|
| 결제창 통과 시점 | **이미 결제됨** | 아직 결제 아님 |
| 서버가 하는 일 | 조회해서 **확인** | 승인을 **요청** |
| 실패 시 | 돈은 나갔는데 상품 못 받음 → 웹훅으로 복구 | 10분 뒤 만료, **돈이 안 나감** |

토스 쪽이 안전 성질이 낫다. 승인 전에는 청구가 없으므로 "결제는 됐는데 상품을 못 받는"
상태가 국내 결제에는 생기지 않는다.

### `2379b9d` 인연링크 국내 결제 — 토스페이먼츠 (다크 런치)

```
주문 생성 → 토스 결제창(method "CARD" = 카드·간편결제 통합)
  → /api/payments/toss/confirm?paymentKey&orderId&amount
  → 서버가 주문 금액과 대조 → 승인 API → PAID → 결과 화면 복귀
```

- **successUrl을 서버 라우트로 뒀다.** 브라우저가 서버에 닿는 순간 바로 승인하기 위해서다.
  결과 화면이 떠서 JS가 돌기를 기다리면 그 사이 창을 닫을 여지가 생기고, 승인은 10분 안에
  해야 한다.
- **입력값 복원**: 궁합 입력은 URL 프래그먼트(`#`)에만 있어 리디렉트를 거치면 사라진다.
  결제 직전에 `sessionStorage`에 맡겨 두고 돌아와서 되돌린다. **이용자 브라우저이지 서버가
  아니므로 미저장 원칙과 충돌하지 않는다** — 탭을 닫으면 함께 사라진다.
- **금액은 주문에 저장된 값으로 승인한다.** 리디렉트로 돌아온 쿼리의 `amount`를 그대로 쓰면
  위변조를 그대로 승인하는 셈이다(토스 문서가 명시적으로 경고). 승인 응답의 `totalAmount`까지
  한 번 더 대조한다.
- Basic 인증은 **시크릿 키 뒤 콜론이 필수**라 `lib/toss.ts` 한 곳에서만 만든다.
  중복 승인은 `Idempotency-Key: orderId`로 막는다.

### `b23b488` naminglink 국내 결제 — 서버 쪽 (다크 런치)

국내 상품 셋(한자 상세·일괄 공개·도장)이 토스로 가고, 글로벌 프리미엄은 포트원 그대로다.

- **세션 확정 로직을 결제사와 분리했다.** `markPremiumSessionPaid`가 포트원 응답 형태
  (`amount.paid`·`id`·`transactionId`)에 직접 묶여 있었다. 정규화된 `PaidRecord`를 받게 바꾸고
  포트원 호출부는 `fromPortOnePayment`로 옮겨 넘긴다.
- 승인 라우트는 하나로 두고 **주문 종류로 가른다**(포트원 웹훅과 같은 규칙):
  `STAMP_DELIVERY`=결제만 확정 / `CANDIDATE_UNLOCK`=처리까지 완료 / 그 외=분석 세션 PAID.
- 돌아갈 자리는 주문 `metadata.returnPath`. **`/`로 시작하는 우리 경로만 허용**(열린 리디렉트 방지).

**남은 것: 화면 세 곳(한자 상세·일괄 공개·도장)에 결제창 호출 붙이기.** 인연링크에서 패턴은
확정됐다.

### SDK·API 사양 (공식 문서·타입 정의로 확인)

```
패키지  @tosspayments/tosspayments-sdk 2.7.1 (v2)
초기화  loadTossPayments(clientKey) → tossPayments.payment({ customerKey: ANONYMOUS })
호출    requestPayment({ method:"CARD", amount:{currency,value}, orderId, orderName,
                         successUrl, failUrl })
성공    {successUrl}?amount=&orderId=&paymentKey=
실패    {failUrl}?code=&message=&orderId=
승인    POST https://api.tosspayments.com/v1/payments/confirm
        Authorization: Basic base64(secretKey + ":")
        body { paymentKey, orderId, amount }
```

환경변수: `NEXT_PUBLIC_TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY` (둘 다 있어야 켜짐)

## 3. 결제 전 고지 — 법적 구멍이었다

### `c83d83a` (인연링크) · `911bf54` (naminglink) 청약철회 동의

전자상거래법 §17② 단서는 즉시 제공되는 디지털 콘텐츠라도 **철회 불가를 알리고 동의를 받는
조치**를 하지 않으면 소비자가 그대로 철회할 수 있다고 정한다. 약관에 적어 둔 것만으로는 그
조치가 아니다. **"다운로드했으니 환불 불가"라는 우리 약관이 실제로는 효력이 없을 수 있었다.**

- 결제 버튼 앞에서 체크박스로 고지·동의. 진입점 **다섯 곳** 전부(인연링크 1 + naminglink 4)
- 서버도 화면을 믿지 않는다 — `withdrawalConsent: z.literal(true)` 필수, 동의 시각을 주문에 기록
- 상품 성격이 갈려 고지도 나눴다: 디지털=제공 시작 / 도장=제작 시작(주문제작, 재판매 불가)
- 상품정보제공 고시 항목, 환불 접수 경로, 미성년자 결제 취소 조항 함께

### `464d97d` 그 상자가 버튼 자리를 차지하고 있었다

타입체크·빌드는 통과하지만 화면이 깨졌다. 2열 그리드에 상자를 세 번째 항목으로 끼워 넣어

**`b94c2ee` CSP가 두 앱에서 크게 달랐다.**
```
naminglink  frame-ancestors 'none'; base-uri 'self'; object-src 'none'   ← script-src 없음
inyeonlink  default-src 'self'; script-src …; connect-src …              ← 전체
```
naminglink는 **스크립트 출처 제한이 사실상 없었다.** 인연링크와 같은 모양으로 조였다.
이 앱만 다른 점: 브라우저가 Supabase를 직접 부르므로(로그인·운영 콘솔) `connect-src`에 그
주소가 필요하다.

**`b6959a6` 인연링크에 레이트리밋이 전혀 없었다.** naminglink는 Supabase RPC로 막고 있는데
나중에 만든 앱에는 그 하드닝이 오지 않았다. `/api/match` 10분 60회, 주문 1시간 10회,
PDF 1시간 30회.

### 실채널 전환 시 반드시
- **`PORTONE_ALLOW_TEST_CHANNEL` 삭제** (로컬·Vercel 양쪽). 채널 키는 브라우저에 노출되므로
  켜 둔 채 운영하면 누구나 테스트 채널로 결제해 돈 없이 상품을 받아 간다
- **실연동 웹훅 재등록 + 시크릿 교체** — 테스트/실연동은 별개다. 채널 키만 갈아 끼우면 운영
  웹훅이 전부 401로 떨어진다
- **첫 실결제에서 CSP 콘솔 확인** — 카드사 인증창은 발급사마다 도메인이 다르다
