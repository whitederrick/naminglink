## 2. 상품 개편 — 2026-08-05 결정

### 무엇을 왜 바꾸는가

- **사주와 오늘의 운세는 다른 것이다.** 사주는 평생, 오늘의 운세는 그 사주에 오늘 일진을 대 본
  하루짜리다. 그런데 「삶의 네 영역」이 **오늘 십신**으로 매긴 값이면서 "내 사주의 성향"으로
  읽혔고, 보관하는 문서의 40%가 하루짜리였다.
- **총운/프리미엄의 차이가 근거 숫자 두 장뿐**이라 팔 이유가 약했다.

### 확정된 것

| | |
| --- | --- |
| 상품 | **「평생 사주와 올해의 운세 리포트」 하나.** ₩990 / US$1.99 |
| 가격 근거 | 궁합은 상대가 바뀌면 재구매하지만 **사주는 1인 1회**. 무료로 주는 곳도 있어 기준선이 낮다 |
| PDF | **평생 + 올해 총운.** 오늘의 운세는 넣지 않는다 |
| 무료 화면 | 개략만 — 원국·일간 한 줄·오행 막대. **강약·용신·십신·영역은 유료** |
| 오늘의 운세 | 무료·화면 전용 + **형제 서비스 채널**(셀프 광고) |
| 해설 | 엔진 템플릿이 본편, **AI는 요약 한 문단**만 |
| 고지 | 참고자료 고지 + **AI 문단 고지**를 자리와 문장을 나눠서 |

### 왜 AI를 한 문단으로 좁혔나

넓게 두면 **이용자가 읽는 글이 사실상 전부 가변**이라, 처음 요구("매번 바뀌지 않게")가
해결된 게 아니라 면책된 것이 된다. 1회 구매·평생 보관·재발급 5회 상품에서는 다르다.

더 큰 이유는 **검증**이다 — 이 영역은 과장·단정이 정책 위반인데, 매번 새로 쓰는 글은 매번
새로 위반할 수 있고 23로케일을 사람이 다 읽어 볼 수 없다. **템플릿은 한 번 검토하면 끝난다.**

## 2.5 코드 리뷰 (2026-08-06) — 한 가지 병이 여덟 곳에서 나왔다

보안·개인정보·성능·품질·표준으로 세 앱을 훑었다. **잘 되어 있는 것**부터: 보안 헤더가 세
사이트 동일(CSP·HSTS preload·`X-Frame-Options: DENY`·nosniff), CSP가 기능이 켜질 때만 열리는
구조, 결제 금액은 DB가 정하고 결제는 결제사에 직접 확인, 주문 표에 생년월일 미저장, 로그에
PII 없음, 본문 받는 라우트 25개 전수 통과.

### 🔴 사주링크 운영에 Supabase 환경변수가 없었다

라이브가 `STORAGE_NOT_READY`를 냈다. 파급이 넷이었다:

1. **푸터가 폴백으로 그려졌다** — 상호 `Naming-Link`(실제 `(주)Platforest`), 등록번호 "준비 중".
   라이브 통신판매 사이트의 법적 고지가 사실과 달랐다(전자상거래법 제10조).
2. **레이트리밋이 전부 통과했다**(`!supabase → return true`).
3. 집계 유실 · **AI 원가 기록 0건**(§7에 "완료"로 적었지만 실제로는 안 돌고 있었다).
4. 상품을 켜면 주문 생성 503.

환경변수를 넣자 전부 복구됐다. **폴백이 셋 다 틀렸던 것**은 따로 고쳤다(아래).

### 왜 같은 패턴이 반복되는가

**앱 목록이 코드 곳곳에 손으로 박혀 있고, 앱을 늘리는 방법이 「복제」이기 때문이다.**

| 자리 | 증상 |
|---|---|
| `verify-route-guards` | 두 앱만 세고 **"ALL PASS"** |
| `verify-env-isolation` | 두 앱만 훑음 |
| `verify-app-split` | 두 앱만 더해 사주 방문 17건이 "새는 값"으로 |
| `api/admin/inyeon-status` | 콘솔이 한 앱만 물음 |
| `admin_analytics_snapshot` | 모르는 앱 → **조용히 naminglink 숫자** |
| 결제 복귀 | 앱마다 사본, 세대마다 하나씩 유실 |
| `company`·`request-guard`·`ops-alert` | 앱마다 거의 같은 사본 |
| Supabase 환경변수 | 새 앱에만 안 들어감 |

셋 다 구조적이다 — ① `packages/core`에 엔진·PDF·env만 있어 나머지는 앱별 사본, ② tsc는
*문자열 배열*과 *있어야 할 코드*를 못 본다, ③ **검사기가 자기 대상을 스스로 정한다.** 목록에서
빠진 앱은 통과한 것이 아니라 **검사받지 않는데** 화면에는 "ALL PASS"가 찍힌다.

### 고친 것

- **`scripts/verify-app-coverage.mjs` 신설**(대조군·주석 제외, 692파일) — 앱 목록을 손으로 적은
  자리를 찾아 실패시킨다. 목록의 원본은 `packages/core`의 `APP_KEYS`이고 `scripts/app-keys.mjs`가
  읽어 준다. **만들자마자 여섯을 잡았다**(위 표의 1~4 + 래퍼 허용 목록 + `verify-order-binding`이
  운영 orders에 행을 넣으면서 환경 가드가 없던 것)
- **콘솔 「서비스 오픈 상태」** — `inyeon-status` 폐지, `APP_KEYS`를 도는 `service-status`로.
  못 물어본 것과 꺼져 있는 것을 화면에서 가른다
- **지표 RPC 마이그레이션**(적용 완료) — 묻는 값을 그대로 쓴다. 모르는 값은 0으로 보인다.
  AI 집계는 `ai_usage_logs.app` 기준(사주가 유료 경로에서 AI를 쓰기 시작해 옛 전제가 깨졌다).
  검증: 방문 582+144+17 = 743 / 전체 743
- **사업자 정보를 `packages/core/src/company.ts`로** — 조회만 앱에 남겨 core가 Supabase를
  모르게 했다. `company-server`가 90줄 사본에서 조회 다섯 줄로 줄었고, **`197-86-02010`이
  저장소 전체에서 한 곳에만 있다**
- **레이트리밋 fail-open에 알림** — RPC 오류에는 알리면서 설정이 아예 없을 때는 알리지 않았다.
  가장 위험한 실패가 가장 조용했다
- **결제 복귀 두 구멍**(§7의 「결론 난 것」)

## 3.5 새 서비스를 붙이는 절차 (2026-08-06 기준)

콘솔·검사기가 `APP_KEYS`를 돌게 바뀌어서, **배선 비용이 사실상 0**이다. 아침까지만 해도
사주링크는 콘솔에 메뉴가 하나도 없었고, 붙이려면 인연링크 화면을 세 벌 복제해야 했다.

### ① `packages/core/src/apps.ts`의 `APP_KEYS`에 한 줄

이것만으로 **자동으로 따라오는 것**: 콘솔 메뉴 그룹 3개(현황·주문·상품) · 경로
`/naming-artist/service/<app>/…` · **통합 대시보드 행과 합계** · 대시보드의 「저쪽 서비스」 링크 ·
서비스 오픈 상태 점검 · 검사기 6종(route-guards · payment-return · app-split · env-isolation ·
app-coverage · reachable-links는 제외, 인자를 받는다).

### ② tsc가 짚어 주는 다섯 곳

`dreamslink`를 임시로 넣고 실측했다. **컴파일이 정확히 다섯 곳에서 멈춘다**(`TS2741`):

```
AdminOperationsConsole.tsx   SERVICE_CONSOLE (분석 종류·문구)  ·  APP_TONE (색)
AdminProductSettings.tsx     BADGE_TONE (색)  ·  COPY (상품 화면 문구)
packages/core/src/apps.ts    APP_LABELS (서비스 이름)
```

빠뜨릴 수 없다 — 빌드가 안 된다. **`Partial<Record<…>>`만 조심할 것**: 그걸 쓰면 누락이 오류가
아니게 되고, 2026-08-04에 실제로 그래서 콘솔 제목이 빈칸으로 떴다 → [[record-appkey-not-enforced]]

### ③ 검사기가 짚어 주는 것 — DB 제약

`orders_service_check` · `site_events_app_check` · `ad_events_app_check` 세 CHECK 제약이 앱
이름을 SQL에 박고 있다. 마이그레이션을 잊으면 **그 앱의 INSERT가 전부 거부되는데, 값 검사는

   자라지 않게 하는 신호이고, 지면은 **로케일마다 실제로 렌더해 장을 세는 것**이 정한다(③).
3. **같은 입력이면 같은 문서.** 달라져도 되는 자리는 `MUTABLE_FIELDS`에만 있고, 코드·검사기·
   고지 세 곳이 같은 목록을 본다.
4. **무료=템플릿(무과금)·유료=엔진+AI 한 문단.** 고트래픽·SEO·애드센스 속도 보호.
5. **결정론.** 점수·간지는 엔진. 과잉약속 회피(운명·건강 단정 금지).
6. **복제 앱은 전수 grep — 라틴과 한글을 함께.** 2026-08-05에 한글 "인연"을 놓쳐 꼬리글이
   `Saju-Link ( 인연 링크 )`로 배포됐다.
7. **새로 만들기 전에 형제 앱을 먼저 볼 것.** 사전 잎의 51%가 이미 번역돼 있었다.
8. **검사기에는 대조군을 넣는다.** 늘 통과하는 검사기는 없는 것과 같다. 값으로 새는지 볼 때는
   **그 항목에만 있는 값**으로 본다 — 흔한 값(오행 이름 같은 것)을 기준 삼으면 멀쩡한 응답을
   잡는다(④).
9. **보내는 것과 그리는 것을 맞춘다.** 응답에 있고 화면에 없으면 새는 것이고, 화면에 있고
   응답에 없으면 화면이 깨진다. "화면이 안 그린다"는 방어가 아니다(④).
10. **green에서만 커밋.** 라이브 표는 후방호환 마이그레이션 + 두 앱 빌드 확인 후에만.
11. **앱 목록을 손으로 적지 않는다.** 원본은 `packages/core`의 `APP_KEYS`이고, `.mjs`는
    `scripts/app-keys.mjs`로 읽는다. `verify-app-coverage`가 어긴 자리를 실패시킨다.
    **검사기에서 이 병이 특히 나쁘다** — 빠진 앱은 통과한 것이 아니라 검사받지 않았는데
    화면에는 "ALL PASS"가 찍힌다(2026-08-06에 여섯 곳이 그랬다).
12. **모르는 값을 그럴듯한 기본값으로 바꾸지 않는다.** 지표 RPC가 모르는 앱을 naminglink로
    바꿔 남의 매출을 보여 주고 있었다. 0은 눈에 띄지만 남의 숫자는 그럴듯해서 안 띈다.
13. **폴백은 사실이어야 한다.** 폴백은 안 쓰이는 값이 아니라 **DB를 못 읽는 순간 법적 고지가
    되는 값**이다. 사업자 정보가 앱마다 따로 적혀 셋 다 틀린 채 라이브에 나갔다.

  함께 지우면 새로고침에 결과가 사라진다
- `download()`가 `Checkout` 전체 대신 `{orderId, paymentId}`만 받는다(복귀 자리엔 결제창 정보가 없다)

**왜 세 앱에서 반복되는가 — 구조는 같은데 코드가 공유되지 않는다.** `packages/core`에는 엔진·
PDF·env만 있고 **결제 흐름은 앱마다 사본**이라 고칠 자리가 늘 세 벌이다. 게다가 베낀 것이
원본이 아니라 이미 한 세대 열화된 사본이었다 — naminglink는 복귀 처리를 세 패널에 각각 손으로
적었고, 인연은 그중 어느 것도 옮기지 않고 새로 쓰며 되돌리기만 넣었고, 사주는 그 인연을 베끼며
되돌리기마저 흘렸다. **빠진 것이 타입이 아니라 "있어야 할 코드"라 tsc가 못 잡는다.**

→ `scripts/verify-payment-return.mjs` **신설**(대조군 내장). 토스를 여는 화면 5개 전수로

### 도메인 연결 — `saju-link.com` (2026-08-06)

**한 번의 재배포로 끝난다.** `NEXT_PUBLIC_SITE_URL` **하나가 스위치**라(`lib/seo.ts`) 값이
`*.vercel.app`이면 `robots.ts`가 색인을 통째로 닫고, 실 도메인으로 바꾸면 robots·canonical·
hreflang·OG·sitemap이 **한꺼번에** 넘어간다. 따로 켜는 스위치를 안 만든 이유가 그것이다.

- DNS는 **A `@` → `216.198.79.1`**(가비아, TTL 3600). **naming-link 때의 `76.76.21.21`을 그대로
  쓰면 안 된다** — Vercel이 신규 도메인에 주는 값이 바뀌었다. 화면에 뜨는 값이 정답이다
- Vercel 「Add Domains」에서 **apex를 입력한다.** www를 넣으면 "A domain cannot redirect to
  itself"가 난다. **`Redirect apex domains to www`는 체크 해제** — 그 항목은 *www를 정본으로*
  삼겠다는 뜻이라, apex를 정본으로 쓰는 우리 설정(`NEXT_PUBLIC_SITE_URL`이 apex)과 어긋난다
- **www는 308(Permanent)로 걸 것.** 기본값이 307(Temporary)인데, 그러면 검색엔진이 www를 apex로
  합치지 않고 따로 색인할 수 있다. naming·inyeon 둘 다 308이라 대조로 잡았다
- 환경변수는 `NEXT_PUBLIC_SITE_URL`과 `NEXT_PUBLIC_ADSENSE_CLIENT`를 **한 번에** 넣고 재배포를
  한 번만 한다(둘 다 빌드 타임 인라인). **빌드 캐시를 끄지 않으면 값이 안 박힌다**

### ① `premiumReport` 절 제거 — 23로케일

상품이 하나로 합쳐진 뒤에도 사전에는 옛 프리미엄 문안이 23벌 남아 있었다. **아무도 읽지
않는데 번역기·검사기의 대상으로는 남아** 있어서, 로케일을 다시 돌릴 때마다 팔지 않는 상품의
상품정보고시를 번역하고 검사했다.

**사전에서 1,257줄이 빠졌다**(로케일 21벌 × 56줄 + ko·en). 함께 정리한 것:

- `Dictionary` 타입에서 제거 — 남기면 21개 파일이 컴파일에서 걸린다
- `verify-i18n`의 강조 허용목록 두 줄. **이 목록은 양방향으로 센다** — 문구를 지우고 목록을
  두면 "여기는 처리돼 있다"고 믿고 다음 사람이 다시 별표를 쓴다
- `verify-product-consistency`의 예외 주석. 절이 없어졌으니 예외도 없앤다

**중괄호 깊이를 세어 잘랐다.** 정규식으로 `}`를 찾으면 절 안의 배열에서 끊긴다 — 드림링크
때와 같은 실패다. 문자열 밖의 중괄호만 세어 깊이가 0으로 돌아오는 줄을 끝으로 삼았다.

「총운 3장 ₩4,900 / 프리미엄 5~6장 ₩9,900」으로 적혀 있었다. **파는 것과 문서가 통째로

### ③ `verify-reachable-links.mjs` — 네 앱

두 앱만 인자로 받고 있었다. 사주·드림에 대해서는 통과가 아니라 **한 번도 돌지 않았다.**

### ④ 머리글 정렬 — 사주만이 아니라 셋 다였다

고친 자리 11곳(사주 5 · 인연 5 · 드림 1). 그리고 **`width`를 필수로 바꿨다** — 전부 넘기게
