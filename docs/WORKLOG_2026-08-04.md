## 1. 안내 "돌아가기"가 남의 서비스로 보냈다 (`ef28746`)

이용자 제보로 시작했다. **글로벌 이름 변환 화면에서 이용 안내를 열면 버튼에 "한자 의미 매칭"이
적히고, 누르면 실제로 그 서비스로 넘어갔다.**

### 원인 — 어디서 왔는지를 묻지 않았다

```ts
backHref={localePath(locale === "ko" ? "/hanja-meaning" : "/global-to-korean", locale)}
```

**로케일만 보고 정하고 있었다.** 한국어면 무조건 한자 의미 매칭, 그 밖이면 무조건 한국 이름
변환이다. 안내를 부른 화면이 무엇이든 상관하지 않았다.

같은 결함이 네 자리에 있었다.

| 어디서 열었나 | 나가던 곳 |
| --- | --- |
| 글로벌 이름 변환 | 한자 의미 매칭 |
| 한글 발음 표기 | 한국 이름 변환 |
| 인연의 결 | 사주 궁합 |
| 푸터(어느 화면이든) | 로케일에 따라 아무 서비스나 |

### 고친 방식

안내로 가는 링크에 `from=<서비스 slug>`를 싣고, `lib/guide-back.ts`가 그것을 되읽는다.

```
lib/guide-back.ts    아는 slug만 받는다. 모르는 값·없는 값은 홈으로.
```

**주소를 그대로 링크로 삼지 않는다.** 아는 slug를 정해진 경로로 옮기는 표라서, 남이 만든
주소로 다른 곳에 보낼 수 없다. `from=bogus`도 홈으로 떨어지는 것을 확인했다.

### `from`이 없으면 홈이다

푸터·소개 화면에서도 안내로 들어온다. 그때 아무 서비스나 하나 골라 두면 **눌러 본 적 없는
입력 화면으로 끌려간다.** 이용자 제보의 절반이 이것이었다("푸터에서 들어갔는데 홈으로 안
돌아간다").

### 출처는 문서까지 따라간다

서비스 → 허브 → 문서 → 허브 → 서비스로 네 번 눌러 나가도 처음 화면으로 돌아온다. 허브의
문서 카드와 문서의 돌아가기 링크가 `from`을 그대로 들고 간다.

### 한 화면에 이용 안내가 둘이다

서비스 화면에는 **본문에 하나, 푸터에 하나** 있다. 본문만 고치면 같은 이름의 링크 둘이 서로
다른 곳으로 나간다. `SiteFooter`에 `guideFrom`을 넘겨 맞췄다.

### 곁다리 — 영어판 안내 목록의 순서

서비스 버튼 줄은 `한글 발음 표기 → 한국 이름`인데 안내 목록은 반대였다. 화면에서 왼쪽에 있던
것이 안내에서 아래에 있으면 같은 두 서비스를 말하는 것으로 읽히지 않는다. 순서를 맞췄다.

## 2. 분석 "시작"이 통째로 날아가고 있었다 (`a86d06d`)

콘솔의 메뉴별 활용에서 **인연의 결이 완료만 있고 시작이 0**이었다.

### 데이터가 먼저 말해 줬다

인연링크 `site_events` 전체(114행):

| 이벤트 | 건수 |
| --- | --- |
| `ANALYSIS_STARTED` GUNGHAP | 1 |
| `ANALYSIS_COMPLETED` GUNGHAP | 5 |
| `ANALYSIS_STARTED` AFFINITY | **0** |
| `ANALYSIS_COMPLETED` AFFINITY | 1 |

인연의 결만의 문제가 아니었다. 그리고 결정적인 대목:

```
09:26:24  PAGE_VIEW           /ko/affinity          입력 화면을 열었다
09:27:13  PAGE_VIEW           /ko/affinity/result   49초 뒤 결과로 넘어갔다
09:27:13  ANALYSIS_COMPLETED  AFFINITY_MATCH        완료는 남았다
          (그 사이 ANALYSIS_STARTED 없음)
```

### naminglink가 대조군이었다

같은 코드인데 이쪽은 멀쩡했다.

| naminglink | 시작 | 완료 |
| --- | --- | --- |
| 한자 의미 매칭 | 9 | 9 |
| 글로벌 이름 변환 | 9 | 9 |
| 한국 이름 변환 | 4 | 4 |
| 한글 발음 표기 | 6 | 6 |

**네 메뉴 모두 정확히 같다.** 코드가 같으니 남는 차이는 하나뿐이다 — **naminglink는 제출해도
화면을 갈아 끼우지 않고 제자리에서 결과를 그린다.** 인연링크는 제출 직후
`window.location.assign`으로 문서를 통째로 바꾼다.

### `sendBeacon`은 기다릴 방법이 없다

beacon은 "떠나는 중에도 보내라"는 뜻이지 **"보낸 것을 확인했다"가 아니다.** 그리고 부르는
쪽에서 기다릴 수단이 없다. `keepalive` fetch로 바꿔 프라미스를 받고, 두 폼이 이동 직전에
그것을 기다린다.

```ts
const started = trackAnalytics({ eventType: "ANALYSIS_STARTED", ... });
...
if (submitAdGateEnabled) { setPendingTarget(target); return; }  // 광고 화면이 시간을 준다
await started;                                                   // 문서를 갈아 끼우기 전에
window.location.assign(target);
```

**광고 관문이 켜진 경로에서는 기다리지 않는다.** 광고 화면이 떠 있는 동안 전송이 끝나므로,
여기서 기다리면 광고만 늦게 뜬다. 느린 망에서 이동이 늦어지지 않도록 **400ms에서 끊는다** —
통계 때문에 이용자를 세워 둘 수는 없다.

### 브라우저로 확인했다

실제로 인연의 결을 제출해 두 행이 들어오는 것을 봤다.

```
01:34:56  ANALYSIS_STARTED    AFFINITY_MATCH  /ko/affinity
01:34:58  ANALYSIS_COMPLETED  AFFINITY_MATCH  /ko/affinity/result
```

이 환경은 광고 관문이 꺼져 있어 **문제였던 그 경로**(곧바로 `location.assign`)로 탔다.

## 3. 소개·문의하기·공지사항이 어디에서도 닿지 않았다 (`3df5684`)

셋 다 만들어져 있었다. 푸터 코드에도 들어 있었다. 그런데 실제로는 **약관 페이지와 도장 주문
화면에서만** 보였다.

푸터가 두 모양이다.

| | 그리는 것 |
| --- | --- |
| `policyMode="links"` | 소개·문의하기·공지사항 + 약관 넷 + 요금·안내·로그인 |
| `policyMode="modal"` | 약관 넷(팝업) + 안내 + 로그인 |

**랜딩·서비스·결과·안내 화면이 전부 modal이다.** 정작 `SiteFooter.tsx`의 주석은 이렇게 적고
있었다 — *"애드센스 심사는 이 두 페이지가 있는지를 보는데, 어디에서도 닿지 않는 페이지는 없는
것과 같다."* **의도와 결과가 어긋나 있었다.**

팝업형에도 셋을 세웠다. **순서는 링크형과 같게 앞에 둔다** — 두 푸터가 다른 차례로 늘어놓으면
화면을 옮길 때마다 같은 항목을 다시 찾아야 한다. 팝업이 아니라 페이지 이동이다. 약관 넷은
동의 직전에 읽는 것이라 화면을 떠나면 안 되지만, 이 셋은 그 자체가 목적지다.

인연링크는 원래 항상 그리고 있어 손대지 않았다.

## 4. 공지사항 페이징 (`4ba9946`)

지금 공지가 셋이라 한 장에 다 들어간다. **화면에는 아무것도 나타나지 않는다.** 쌓인 뒤에
붙이려 하면 그때는 이미 긴 목록을 보고 있는 사람이 있다.

한 장에 열. 없는 장은 마지막 장으로, 숫자가 아니면 첫 장으로 잘라 낸다 — 링크는 우리가
만들지만 주소는 남이 고쳐 넣을 수 있고, **빈 화면을 보여 주면 공지가 사라진 것처럼 읽힌다.**
첫 장 링크에는 `page`를 붙이지 않는다(같은 화면이 두 주소를 갖지 않게).

확인은 한 장에 둘로 잠깐 낮춰서 했다. `page=99` → 마지막 장, `abc`·`0`·`-1` → 첫 장.

### 팝업으로 하지 않은 이유

"페이징도 없이 위에 쌓이기만 하는데 왜 페이지인가"라는 물음이 있었다. 기준은 **떠나면 안 되는
자리에서 읽는가**다. 약관 넷은 동의하면서 읽으므로 팝업, 공지는 목적지라 페이지다. 팝업으로
바꾸면 **개별 공지에 링크를 못 걸고**(응대할 때 "이 공지를 보십시오"가 안 된다), 색인에서
빠지고, 검색으로 못 찾는다. 페이징은 건수가 늘면 붙이면 되고, 그것도 페이지일 때만 된다.

## 5. 운영 콘솔이 확인 전에 틀부터 그렸다 (`ca90e99`)

주소를 치면 대시보드 틀이 잠깐 보였다가 로그인 화면으로 바뀌었다.

**값은 새지 않았다.** 아직 받아오기 전이라 내용이 비어 있었다. 다만 로그인 없이 받은 HTML에
`대시보드 · 회원 · 운영자 · AI 사용량`이 들어 있었다. 운영 화면의 구성을 아무에게나 보여 줄
이유가 없고, 껍데기가 번쩍이는 것 자체가 고장처럼 보인다.

서버가 운영자로 인정한 뒤에만 그린다. **자물쇠는 그대로 서버에 있다** —
`/api/admin/operations`가 토큰을 보고 401·403을 돌려준다. 이것은 화면 쪽 정리다.

### 같이 막은 것

`fetch`나 `json()`이 던지면 그 함수가 도중에 끝나 **화면이 "확인 중…"에서 영영 멈춘다.**
감싸고, 무엇이 잘못됐는지 적고, `다시 시도`를 붙였다. **500은 화면을 연다** — 인정은 받았는데
자료만 못 불러온 것이라 무엇이 잘못됐는지 보이는 편이 낫다.

훅을 전부 부른 뒤에 나간다. 앞에서 반환하면 화면이 바뀔 때 훅 개수가 달라져 React가 터진다.

문구를 "권한이 없습니다"로 두지 않았다 — 주소가 맞는지 틀린지를 알려 주는 셈이 된다.

## 6. 제출 버튼이 없는 광고를 예고했다 (`343c07e`)

인연링크 버튼이 **"광고 확인 후 궁합 보기"**인데 누르면 광고 없이 바로 결과가 나온다. 광고
단위가 없어 관문이 꺼져 있기 때문이다. **아직 광고 신청 전이라 이 상태가 한동안 이어진다.**

문구를 지우지 않고 하나 더 뒀다.

```
광고 단위 없음  →  submitNoAd   궁합 보기 / 인연의 결 확인
광고 단위 있음  →  submit       광고 확인 후 궁합 보기 / …
```

**환경변수에 광고 단위를 넣으면 관문과 문구가 함께 켜진다.** 그때 사전을 다시 고칠 일이 없다.

### 문구는 새로 번역하지 않았다

기존 광고 문구가 **"광고를 보고 + X를 한다"** 꼴이라 **앞 절만 떼었다.** 뒤 절은 원문 그대로다.

```
de  Werbung ansehen und Kompatibilität prüfen  →  Kompatibilität prüfen
ja  広告を見て相性を確認                        →  相性を確認
ar  شاهد الإعلان لرؤية نتيجة العلاقة            →  عرض نتيجة العلاقة
```

새로 옮기는 것보다 어긋날 자리가 적다. 23로케일 46개이고, **타입에 넣었으므로 로케일이 빠지면
컴파일이 멈춘다.**

### 버튼을 비활성화하지 않은 이유

"광고가 붙을 때까지 버튼을 막자"는 안이 있었다. 그 버튼이 두 메뉴의 **유일한 실행 버튼**이라
누를 수 없게 하면 인연링크가 사실상 닫힌다. 색인이 552개 들어가 있고, 애드센스 심사자가
들어와 버튼이 죽어 있으면 "콘텐츠 없는 사이트"로 반려된다 — **전면 잠금·클로킹은 심사와 양립
불가**라는 기존 판단과도 어긋난다. **문제는 서비스가 아니라 문구였다.**

### 무료로 열려 있는 기간이 길어지는 것

걱정은 "지금 무료처럼 보이게 하면 나중에 광고를 붙일 때 이탈하지 않겠나"였다. **문구는 그
기대를 만들지 않는다. 실제 경험이 만든다.** 지금도 누르면 광고 없이 즉시 나오므로 이용자는
이미 "바로 나온다"로 배우고 있다. 문구를 남겨 둬도 나중의 이탈은 같고, 지금은 혼란만 는다.
게다가 인연링크 전체 방문자가 38명이라 지킬 기반도 아직 없다.

## 8. 오늘 걸린 함정

- **배포 확인 문자열이 옛 문구의 부분집합이었다.** `궁합 보기`로 찾았는데
  `광고 확인 후 궁합 보기` 안에 그대로 들어 있어 **배포 전인데 통과**해 버렸다. 사라져야 할
  쪽(`광고 확인 후`)을 기준으로 다시 잡았다. **새 값이 옛 값에 포함되는지 먼저 볼 것.**
- **`.env.local`이 CRLF가 아니라 값 끝에 `\r`이 붙어 있었다.** Supabase 키를 그대로 쓰면
  `Invalid API key`가 난다. `tr -d '\r"'`로 털어야 한다.
- **인연링크 dev 서버를 둘 띄울 수 없다.** 같은 `.next`를 보므로 두 번째가 조용히 안 뜬다.
  광고를 켠 쪽 화면을 확인하지 못한 이유가 이것이다.
- **PowerShell `Stop-Process`가 막혀 있다.** Git Bash의 `taskkill //PID <번호> //F`는 된다
  (`pkill`은 없다). PID는 `Get-NetTCPConnection -LocalPort <포트> -State Listen`으로 찾는다.
- **`tsx`가 설치돼 있지 않다.** `scripts/verify-i18n.ts`를 못 돌린다. 이번 변경이 그 검증기가
  보는 네 가지(자리표시자·`**강조**`·`\n`·배열 길이)에 해당하지 않아 직접 대조했다.

## 9. 전수 코드 리뷰

앞의 일곱 건을 배포한 뒤 저장소 전체를 훑었다. **어제 감사(`AUDIT_2026-08-03.md`)가 본 보안
표면은 되풀이하지 않고**, 그 감사가 안 본 각도 — 정합성·에러 처리·경계값 — 를 봤다.

### 먼저 돌린 것

검사기 **23종 전부**. `tsx`가 naminglink 쪽에만 설치돼 있어 그 바이너리로 양쪽을 돌렸다
(`../naminglink/node_modules/.bin/tsx`). 세 개는 `--tsconfig scripts/tsconfig.sweep.json`이
필요했다 — `server-only` 스텁이 거기 걸려 있다.

전부 통과했다. 회귀 스냅샷 변동 없음, 번들에 서버 비밀 0건, 격리 스윕 503개 파일 ALL PASS.

### 라우트 46개 전수 조사

레이트리밋·인증·스키마·본문 제한 네 항목으로 표를 떴다. **빈칸 대부분이 오탐이었다** —
`account/*`는 `getAuthenticatedUser`, `premium-reports/[sessionId]/*`는 접근 토큰 해시,
`payments/*`는 서명·금액 대조로 각각 막혀 있었다. 키워드로 세면 이렇게 된다.

남은 것을 직접 읽어 진짜를 넷 찾았다.

## 10. 리뷰에서 나온 넷

### 10-1. 한 결제로 여러 벌 — 두 앱 같은 모양

주문 metadata를 **읽고 → 판단하고 → 나중에 쓴다.** 그 사이가 비어 있어 동시에 들어온 요청
둘이 **둘 다 "아직 결속 안 됨"을 보고 둘 다 통과**한다.

| | 새던 것 |
| --- | --- |
| `inyeonlink/api/report/pdf` | 한 결제로 **서로 다른 사람의 리포트**가 나간다 |
| `naminglink/api/candidates/unseal-all` | 주석이 *"990원에 무제한이 된다"*고 적어 둔 바로 그것 |

조건을 쓰기에 붙여 먼저 도착한 하나만 성공하게 했다. 못 쓴 쪽은 다시 읽어 자기 것인지
확인한다 — **같은 결과를 두 창에서 여는 정상 경우가 여기 걸린다.**

인연링크는 결속을 **렌더 앞으로** 옮겼다. 뒤에 두면 그사이 다른 입력이 들어와도 막을 것이
없다. **발급 횟수는 그대로 렌더 뒤에 적는다** — 결속이 끝났으므로 그때 나가는 것은 같은
사람이 자기 파일을 다시 받는 것뿐이고, 렌더 실패에 횟수를 소모하지 않는 성질이 더 중요하다.

**검사기를 남겼다**(`scripts/verify-order-binding.mjs`). PostgREST의 JSON 경로 필터
(`metadata->>key=is.null`)가 **문법만 맞고 매칭이 안 되면 첫 결제 해제가 통째로 막히면서도
코드는 멀쩡해 보인다.** 실제 DB에 동시 다섯을 던져 하나만 성공하는 것까지 확인한다.

### 10-2. 인연링크 집계만 본문 제한이 없었다

다른 다섯 라우트와 naminglink의 같은 라우트는 전부 자르는데 **이 하나만** `request.json()`을
그대로 불렀다. 게다가 레이트리밋보다 먼저 파싱했다. 4KB로 자르고 순서를 바꿨다.

**어제 감사가 "오탐이었다, 다섯 라우트 전부 있었다"고 적은 자리다.** 아홉 개 중 다섯을
표본으로 보고 끝냈기 때문에 빠진 하나를 못 봤다.

### 10-3. 중국어 랜딩 부제에서 첫 문장이 빠져 있었다

```
en   All you need is a birth date.
We combine Saju … and show it as a match rate.
zh   同时推算传统命理的八字合婚与生肖合婚，以匹配度呈现给您。      ← 앞 문장 없음
```

"생년월일 하나만 있으면 된다"는 이 서비스의 핵심 문구인데 중국어판에만 없었다.

### 10-4. naminglink 집계도 같은 전송으로 통일

지금 고장 나서가 아니다. **그쪽은 화면을 갈아 끼우지 않아 숫자가 맞는다.** 다만 이 근처에
이동이 하나 들어오는 순간 §2의 유실이 아무 표시 없이 재현된다. 우연히 안전한 상태를 남겨
두지 않는다.

## 12. 왜 자꾸 빠지는가 — 그리고 무엇을 했나

오늘 여덟 건 중 **넷이 같은 원인**이었다.

| 원인 | 오늘 나온 것 |
| --- | --- |
| 같은 일을 두 벌·23벌씩 해야 한다 | 라우트 아홉 중 여덟에만 본문 제한, 푸터 두 모드 중 하나에만 링크, 결속 경합이 두 앱에 |
| 검사가 "있는지"만 보고 "닿는지"는 안 본다 | 소개·문의·공지가 파일도 sitemap도 있는데 화면에서 안 보임 |
| 화면을 안 열어 봤다 | 돌아가기·버튼 문구·콘솔 깜빡임 — 한 번 눌렀으면 즉시 보일 것들 |
| 시간이 지나 전제가 바뀐다 | "광고 확인 후"는 **쓸 때는 맞는 말**이었다 |

**표본으로 끝낸 것이 어제의 실수였다.** 다섯을 보고 "전부 있다"고 적었고, 그 기록이 다음
사람을 안심시킬 뻔했다.

그래서 손이 아니라 검사기가 세게 했다.

```
scripts/verify-route-guards.mjs       무인증 라우트가 본문 크기·호출 횟수를 재는가 (서버 불필요)
scripts/verify-reachable-links.mjs    화면에서 실제로 링크에 닿는가 (dev 서버 필요)
```

- `route-guards`는 **관문 뒤에 있는 라우트는 요구하지 않는다.** 위협 모형이 다르다 —
  관리자가 큰 JSON을 보내는 것은 막을 일이 아니다. 그래서 **예외 목록이 0개**다.
  처음에는 21건이 걸렸는데 하나씩 판정해 보니 "본문을 안 읽는 라우트"와 "내가 못 알아본
  관문"이었다. **무더기로 예외 처리하지 않고 규칙을 고쳤다.**
- `reachable-links`는 화면 여섯 종류를 돈다. 한 화면만 보면 그 화면이 쓰는 푸터만 보게 된다.

**둘 다 대조군을 넣었다.** `route-guards`에는 **실제로 있었던 결함 코드**를, `reachable-links`
에는 있을 수 없는 링크를 넣어 검사가 살아 있는지 스스로 증명하게 했다. 검사 대상이 0개면
통과가 아니라 실패로 떨어진다 — **조용히 통과하는 검사기는 없는 것보다 나쁘다.**

진짜로 잡는지도 확인했다. 고친 파일을 되돌려 놓으니 정확히 그 줄을 물었고, 푸터 링크를
지워 놓으니 오늘 아침의 그 결함이 그대로 재현되며 잡혔다.
