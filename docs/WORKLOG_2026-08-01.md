## 1. 방법을 먼저 바꿨다

어제 감사는 **표본**이었다. 로케일 열 개를 렌더하고 `[4]`번 페이지 하나씩만 PNG로 봤다.
하필 그 페이지에 가나가 적어서, 일본어가 깨진 채로 통과했다.

PDF의 결함이 눈에 안 띄는 이유는 세 겹이다.

1. 서체에 글리프가 없어도 **렌더는 성공한다.**
2. 없는 글자는 빈 네모가 아니라 **내장 Helvetica로 되돌아가 엉뚱한 라틴 글자**가 찍힌다
   (아랍어 `عبد`가 `)JFJ5D'`로 나온다).
3. 텍스트를 추출하면 **원래 문자열이 그대로** 들어 있다. 그래서 자동 검사도 눈도 못 잡는다.

그래서 눈 대신 **서체 커버리지**를 본다. 검사기 셋을 만들었다.

| 검사기 | 무엇을 보는가 | 표본인가 |
| --- | --- | --- |
| `apps/*/scripts/verify-pdf-glyphs.ts` | 23로케일 **모든 문구**를 실제 라우팅에 태우고 배정된 서체의 cmap과 대조 | 전수 |
| `apps/*/scripts/render-*-scripts.tsx` | 문자 체계 열 개로 실제 렌더 → PNG | 표본(레이아웃 전용) |
| `scripts/audit-pdf-glyphs.py` | **만들어진 PDF**에서 문자별로 어느 서체로 찍혔는지 역추적 | 산출물 전수 |

셋이 겹치지 않는다. 첫째는 `MixedText`를 지나는 문구를, 셋째는 그것을 지나지 않는 문구까지
본다. 레이아웃(넘침·겹침·빈 지면)은 여전히 **PNG로 눈으로** 봐야 한다.

## 2. 찾은 것

### ① 일본어·중국어 PDF가 통째로 깨져 있었다

`NotoSansCJKkr-Naming.otf`는 **한국 인명용 한자만** 담은 9,088자 서브셋인데, 라우팅은 가나까지
이 서체로 보내고 있었다. 코드 주석에도 "한자·가나는 CJK 서브셋으로"라고 **적혀 있었다** —
의도는 적혀 있고 사실은 아니었다.

```
ja   가나 전부 + 일본 신자체 67자   →  Helvetica로 되돌아가 라틴 쓰레기
zh   중국 간체 259자                →  같음
```

일본어 표지의 「インヨンリンク」가 `¤óèóêó¯`로 찍히고 있었다. 판매 전이라 실제 피해는 없다.

### ② 화살표 `→`가 23로케일 전부에서 깨져 있었다

`{from} → {to}` 한 줄인데 `NotoSans`에 U+2192 글리프가 없다. 로케일과 무관하게 쓰는 문구라
**모든 언어에서** 깨져 있었다. 한 글자짜리라 PNG를 봐도 눈에 띄지 않는다.

### ③ 한자·태국어 뒤의 문장부호가 서브셋으로 끌려갔다

`splitScriptRuns`는 공백·괄호를 **앞 run에 붙였다.** 한자 뒤의 `)` 하나가 CJK 서브셋으로
가는데 거기엔 라틴 괄호가 없다. 태국어는 `()·—` 넷이 같은 이유로 깨졌다.

### ④ CJK 줄바꿈 자리마다 하이픈이 찍혔다

`@react-pdf/textkit`은 줄이 바뀌는 자리에 그 줄 마지막 서체의 하이픈을 넣는다
(`insertGlyph(HYPHEN)`). 라틴에서는 맞지만 일본어·중국어에서는 **줄마다 `-`가 달린다.**
서체에 하이픈이 없으면 대신 `.notdef` 빈 네모가 찍혔다.

이 하이픈이 나오는 조건이 **우리가 만든 run 경계**라는 것이 원인 규명의 핵심이었다. 가나와
한자를 다른 서체로 가르면 그 경계마다 끊을 자리가 생기고, 거기서 줄이 바뀌면 하이픈이 붙는다.

### ⑤ 아랍어·크메르어 이용자의 **이름**이 깨져 나가고 있었다 (인연링크)

어제 결정으로 그 두 로케일은 PDF를 영어로 낸다. 그런데 **이름은 여전히 아랍 문자다.** 서체를
등록하지 않았으니 이름만 Helvetica로 되돌아가, 돈을 받고 파는 문서에 사는 사람의 이름이
`)JFJ5D'`로 찍히고 있었다.

실측으로 갈랐다 — **죽는 것은 문단이지 이름이 아니다.**

```
영어 문서 + 아랍어 이름(24자, 상한)   두 상품 모두 렌더 성공
영어 문서 + 크메르어 이름             성공
문서 전체가 아랍어                    실패 (reorderLine)
문서 전체가 크메르어                  실패 (xCoordinate가 null)
```

### ⑥ naminglink에는 ar·km 대책이 아예 없었다

크메르어는 **렌더가 실패**하고(결제하고 파일을 못 받는다), 아랍어는 실패하지 않는 대신
**지면이 뒤엉켜 읽을 수 없다.** 오류가 안 나서 더 위험했다.

## 3. 고친 방법

### 서체 둘을 다시 만들었다 (두 앱 공통 파일)

- `NotoSansCJKkr-Naming.otf` — 9,088자 → **21,823자**(U+4E00–9FFF 전체 + 호환 한자 + 기존
  서브셋). **같은 Noto Sans CJK KR**에서 다시 떠서 한국 한자 자형은 그대로다. 5.5MB → 10.8MB.
- `NotoSansJP-Kana.ttf` — 새로 만들었다(337KB). 가나 + CJK·전각 문장부호 + 화살표·기호.
  **한자는 일부러 넣지 않았다** — 겹치면 같은 글자가 문서 안에서 두 서체로 찍힌다.

둘 다 **U+002D 글리프를 비워** ④를 막았다. 라우팅이 진짜 하이픈은 라틴 서체로 보내므로,
이 서체의 하이픈은 textkit이 자동으로 넣는 그것뿐이다.

렌더 시간은 그대로다(ko 1,157ms → 1,157ms). fontkit이 쓰는 글리프만 읽기 때문이다.

### 라우팅 (`packages/core/src/pdf/script-runs.tsx`)

- 가나를 한자에서 **떼어 냈다**(한자보다 먼저 판별해야 한다).
- CJK·전각 문장부호와 화살표·기호를 가나 서체로 보낸다.
- 중립 문자는 **문장부호를 가진 패밀리(라틴·한글)로 이어질 때만** 그 run에 붙이고, 그 밖에는
  기본 폰트로 보낸다(③).

### naminglink의 판별 규칙 중복을 없앴다

`report-fonts.tsx`에 `splitScriptRuns` **복사본**이 있었다. 인연링크에서 고친 것이 이쪽에
오지 않아 결함이 한쪽에만 남는 구조였다. 지웠고, 이제 두 앱 모두 `@naminglink/core`를 쓴다.

두 앱 다 패밀리→파일을 `FONT_FILES` 표 하나로 모았다. **등록과 검증이 같은 표를 본다** —
목록을 따로 적어 두면 어긋난다는 것이 오늘 배운 것이다.

### ar·km 대책 (naminglink)

`lib/pdf/pdf-language.ts`가 판단을 한곳에 가둔다(인연링크의 `pdfLocale`과 같은 꼴).

| 상품 | 처리 |
| --- | --- |
| Korean Name Premium | 해설을 **영어로 생성**한다(모델에 넘기는 언어를 바꾼다) |
| Hangul Name Art | 화면 결과를 복사하는 구조라 **결제 후 영어로 옮긴다**(사용자 결정) |
| Name Art Pack | 문단이 없다 — 이름만 실리고 이름은 제 문자로 찍힌다 |
| 프리미엄 한자 | 한국어 전용 흐름이라 해당 없음 |

`hangul-art-translate.ts`는 **번역이지 창작이 아니다.** 옮길 문장만 주고 없는 사실을 더하지
말라고 못 박는다. **미결제 주문에 모델 비용이 붙지 않도록** 주문 시점이 아니라 생성 시점에
둔다. 관리자 테스트 라우트도 같은 판단을 쓴다 — 테스트만 아랍어로 만들어 보고 "된다"고
착각하는 일이 없어야 한다.

결제 전 고지는 23로케일로 넣었다(`checkout-consent/pdf-language-notice.ts`, `Record`라 로케일이
늘면 컴파일이 깨진다). 문구는 인연링크의 같은 고지와 **같은 문장**이다.

### 인연링크는 아랍어·크메르어 서체를 **등록**한다

문서는 그대로 영어로 내되(문단이 죽으므로), 서체를 등록해 **이름이 제 문자로 찍히게** 했다(⑤).


눈으로 확인한 지면: 인연링크 ja·hi·th·zh와 **영어 문서 + 아랍어 이름**, naminglink th·ja·zh·
프리미엄 한자·아트 페이지(아랍어 이름). 넘침·겹침·빈 지면 없음.

`audit-pdf-glyphs.py`가 아랍어 문서에서 한두 글자를 잡는 것은 **거짓 양성**이다. PDF에서
글자를 뽑을 때 양방향 재정렬이 일어나 글자가 옆 span에 붙는다. 라우팅 자체를 보는
`verify-pdf-glyphs.ts`에서는 나오지 않고, PNG로도 멀쩡하다.

## 5. 남은 것

- **아랍어·크메르어 문단은 여전히 못 낸다.** `@react-pdf/renderer`가 최신(4.5.1)이라 올릴
  버전도 없다. `render-report-scripts.tsx`가 그 자리를 계속 렌더하며, **성공하면 알려 준다** —
  그때가 두 앱의 `PDF_FALLBACK_TO_EN`을 비울 때다.
- 한글 아트 PDF의 영어 번역은 **모델을 실제로 불러 확인했다** — 아랍어 해설 다섯 필드가 4초에
  영어로 바뀌고, 한글 표기·로마자·음절은 그대로였다. 그 결과로 PDF까지 뽑아 이름이 아랍 문자
  그대로 찍히는 것도 봤다(`Hangul spelling of عبد الرحمن`).
  **남은 것은 결제→생성 라우트를 실주문으로 통과시키는 것뿐이다** — 결제 키가 없어 그 배선만
  못 태웠다. 결제를 켜면 ar 주문 한 건으로 확인할 것.
- 오픈 순서는 그대로다: 실 도메인 → 애드센스 승인 → 슬롯 ID → 결제 키.
