_2026-08-27. 사용자 결정: **기존 사전은 기준으로 못 쓴다. 원문(주공해몽·밀러 등)에서
새로 만든다.**_

기존 218개 상징은 2026-08-06에 근거 없이 만들어졌고, 그 위에 `source: "tradition"`
라벨이 기계적으로 붙어 **99%가 "전통 근거 확인됨"으로 위장**돼 있었다(CLAUDE.md §21).
12차례의 배치는 그 위에 근거를 덧대는 작업이었고, 기준 자체를 바꾸지 못했다.

## 1. 새 기준 — 인용문이 없으면 항목이 존재할 수 없다

**문제의 뿌리는 `source`가 문자열 라벨이었다는 것이다.** 「tradition」이라고 적기만 하면
근거가 있는 것이 됐고, 그래서 거짓이 가능했다.

새 스키마는 **인용문 자체를 필수 필드로** 만든다 — 원문이 없으면 항목을 쓸 수 없다.

```jsonc
{
  "id": "star",
  "term_ko": "별", "term_en": "star",
  "aliases": ["별똥별"],
  "meanings": [
    {
      "context": "별이 떨어짐",
      "interpretation_ko": "병이나 관재가 생길 조짐",
      "interpretation_en": "a sign of illness or legal trouble",
      "polarity": "negative",
      "cite": {                          // ← 필수. 없으면 스키마 위반
        "work": "zhougong",              // zhougong | miller
        "original": "星落有病及官事",      // 원문 그대로
        "locator": "天地日月星辰",         // 갈래(주공해몽) 또는 표제어(밀러)
        "translation_ko": "별이 떨어지면 병이나 관재가 생긴다"
      }
    }
  ]
}
```

**강제 방법**(라벨은 또 거짓말할 수 있으므로 코드로 막는다):
- `cite.original`이 **실제 원문 파일에 그 문자열로 존재하는지** 대조한다. 지어낸 인용은
  대조에서 걸린다.
- 대조하는 검사기를 관문에 넣고, **인용 없는 의미가 하나라도 있으면 빨간불**.

이것이 지금 구조와의 결정적 차이다 — 지금은 「전통이다」라고 **말하면** 되지만,
새 구조는 「원문 어디에 이렇게 적혀 있다」를 **대조당한다**.

## 2. 단계

### 1단계 — 스키마와 관문을 먼저 세운다

빈 사전 + 검사기부터 만든다. **항목을 하나도 안 넣은 상태에서 검사기가 도는지** 본다
(CLAUDE.md §11 — 관문은 비싼 단계 **앞**에).

- 새 타입 정의(`cite` 필수)
- `verify-dream-cite.ts` — 모든 의미에 `cite`가 있는가 · `cite.original`이 원문 파일에
  실제로 있는가 · 지어낸 인용을 넣은 대조군이 빨간불을 내는가
- 산출물: 항목 0개짜리 새 사전 파일 + 도는 검사기

### 2단계 — 원문에서 후보를 기계로 뽑는다

사람이 988줄·2,257표제어를 눈으로 훑으면 빠뜨린다. 먼저 **기계로 목록을 만든다.**

- 주공해몽: 27개 갈래별로 각 줄의 주어를 뽑아 후보 상징 목록화
- 밀러: 표제어 2,257개가 곧 후보(문단 단위로 상황이 갈림)
- 산출물: `docs/DREAM_SOURCE_INVENTORY.md` — 원문이 실제로 말하는 것 전수 목록

### 3단계 — 후보를 걸러 새 사전에 넣는다

전부 넣지 않는다. 거르는 기준을 **먼저 정하고 적어 둔다**:

- **한국 이용자가 실제로 꿀 만한 것인가** — 밀러의 19세기 서양 물건(마차·코르셋 등)은 뺀다
- **상충하면 한국을 우선한다**(사용자 확정) — 까치 울음처럼 한국 통설과 반대인 밀러 항목은
  안 쓴다
- 배치 단위로 넣고, 배치마다 검사기·손 확인을 돌린다(지금 굳은 절차 그대로)

### 4단계 — 기존 218개는 버린다

**대조하지 않는다.** 근거 없이 만든 것을 기준으로 삼아 「이건 살리고 저건 버리고」를
가리면, 그 판단 자체가 다시 그 쓰레기 위에 서게 된다. 새 사전은 원문에서만 나온다.

기존 파일(`dream-symbols.data.json`)은 **6단계에서 통째로 교체된다.** 그때까지 지우지
않는 이유는 서비스가 라이브라 그 파일이 없으면 화면이 죽기 때문이지, 참고하기 위해서가
아니다.

우연히 같은 상징이 새 사전에도 있으면(돼지·뱀 등 원문에 실제로 있는 것) 주소가 살아남는
것이고, 그건 **결과이지 목표가 아니다.**

### 5단계 — 죽는 주소를 정리한다

새 사전에 없는 상징의 주소는 색인돼 있다(218 × 23 = 5,014개 중 상당수).
**410(Gone)으로 낼지, 사전 목록으로 301 보낼지**를 정해야 한다 — SEO 영향이 커서
사용자와 정한다.

### 6단계 — 갈아끼운다

새 사전이 기존을 대체한다. 8개 파일이 읽는 자리를 바꾸고, 관문 전체 + 빌드로 확인.

## 3. 이번에 지킬 것 (오늘 어긴 것들)

- **"검사 안 함"은 통과가 아니다.** 오늘 `verify-guide-numbers`가 20건을 "검사 안 함"으로
  넘기는데 마지막 `ALL PASS`만 보고 넘어갔다. 검사기 출력은 끝줄만 읽지 않는다.
- **검사기가 무엇을 안 보는지 먼저 묻는다.** 오늘 그 검사기는 23개 로케일 중 **1개만**
  읽고 있었다. 새 검사기를 만들 때 적용 범위부터 적는다.
- **수는 스크립트로 센다.** 오늘 손으로 센 수(72)가 실제(74)와 달랐고, 그 차이가 진짜
  결함이었다.
- **근거를 커밋 메시지에만 적지 않는다.** 데이터에 실제로 들어갔는지 확인한다.
- **범위를 내 판단으로 넓히지 않는다.** 단계마다 사용자에게 확인받고 넘어간다.

## 4. 지금 결정이 필요한 것

1. **1단계(스키마+관문)부터 시작해도 되는가**
2. **현대 사물(엘리베이터·은행·시험 등)은 어떻게 하는가** — 원문에 있을 수가 없다.
   아예 안 만들지, 「원문 근거 없음」이 화면에 드러나는 별도 갈래로 둘지.
   **기존 것을 살리는 게 아니라, 새로 만들 때 넣을지 말지의 문제다.**
3. **오늘 커밋 안 된 23개 로케일 숫자 수정** — 사전을 새로 만들면 숫자는 어차피 바뀐다.
   다만 「숫자를 손으로 박지 말고 자리표시자로 둔다」는 고침 자체는 새 사전에도 그대로
   필요하다(그래서 낡지 않는다). 살리는 쪽을 권한다.
